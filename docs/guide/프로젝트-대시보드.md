# 프로젝트 대시보드 (v2) — 설계·설정·운영

v1(기관 메일 수집·원본 보관·중복/실패 이력)은 메일 스킬의 mailon 동기화와 첨부 아카이브가 이미 한다.
이 문서는 그 위에 얹은 v2 — 분석 → 담당자 검토·확정 → 승인된 프로젝트 데이터 → 웹 대시보드 → 실행 기록 — 의
규약을 단독으로 소유한다. 사용 시나리오는 [소개](../기능소개/프로젝트-대시보드-v2.md).

## 1. 상자 → 모듈 (`automation/project_board/`)

| 단계 | 모듈 | 불변식 |
|---|---|---|
| 입력(v1 결과) | `sources.py` | MailOn `state.db`·저장 markdown·첨부 파일을 **읽기만** 한다. 경로 해석은 메일 래퍼와 같다(`MAIL_WRAPPER_REPO`·`MAIL_WRAPPER_DB`, 기본 `~/.hermes/mailon-runtime/current`). 회의록은 `meeting_minutes.finalized_view` 로 부록 위만 읽는다(「산출물 출처 규칙」) |
| 분석 | `llm.py`·`analysis.py`·`prompts/project-analysis-v1.md` | 제공자 인터페이스 하나. 기본 `hermes` = `automation.codex_llm`(계정 주 모델·폴백, 코드에 모델 이름 없음). `openai-compatible` 은 설정으로만 고른다. 답은 엄격 파싱 — JSON 아니면·날짜 아니면 실패(추측 금지), `relevant:false` 면 제안 없음 |
| 검토·확정 | `proposals.py`·`proposal_gate.py`·`proposal_render.py`·`cli revise` | 제안 하나 = 카드 하나. `action_hash` = 정규화 제안 JSON 의 sha256. 수정은 같은 key 의 새 판 → 공용 lifecycle 이 미결 옛 카드를 지우고 같은 스레드에 새 카드. ✅/⛔ 된 제안은 고치지 않는다 |
| 승인된 항목만 반영 | `proposal_watch.py`·cron `project-board-watch`(2분) | 소유자(봇 아님) 리액션만, ⛔ 우선. 반영 직전 동결 파일을 다시 해시해 레코드와 대조 |
| 승인 데이터 | `board_store.py`(SQLite `~/.hermes/project-board/board.db`, 0600) | 제안 id 로 멱등. 진행 기록은 상태·진척만 바꾸고 할 일을 만들지 않는다 |
| 대시보드 | `dashboard.py`·`server.py`·사용자 유닛 `autophagy-project-board` | 자체 완결 HTML(외부 폰트·CDN 없음). 서버는 루프백 전용(비루프백 bind 거부)·토큰 필수·체크 POST 는 토큰 2중+같은 Origin |
| 실행 → 기록 | `cli progress`·대시보드 체크 | 기록마다 이벤트 원장 한 줄, 대시보드 파일 재생성 |
| 외부 메일 | `cli digest --request-mail` | 메일 스킬 `compose --attachment` 의 **표준 메일 승인 카드**로만 나간다. 이 패키지는 메일을 보내지 않는다 |

## 2. 설정 (`~/.hermes/project-board/config.json`, 없어도 됨)

```json
{
  "llm": {"provider": "hermes"},
  "analyze": {"enabled": false, "max_per_tick": 5},
  "dashboard": {"port": 8810},
  "digest": {"to": ["<수신 주소>"], "subject": "프로젝트 현황 일일 요약"}
}
```

- 로컬 LLM 으로 바꾸기: `"llm": {"provider": "openai-compatible", "base_url": "http://127.0.0.1:8000/v1",
  "model": "<서버의 모델 id>", "api_key_env": "<키가 필요하면 환경변수 이름>"}`. 모델 id·주소는 이 파일에만 둔다.
  확인: `python3 -m automation.project_board status` 의 `MODEL` 줄.
- 확정 회의록: `analyze.enabled` 가 켜져 있고 `DRIVE_PUBLISH_ENABLED=1` 이면 같은 틱이 Drive 산출물 트리의
  `회의록/<과제>/<연도>/*.md` 도 읽는다(읽기 전용 — 폴더를 만들지 않는다). 첫 틱은 지금 있는 회의록을 "본 것" 으로만
  적고(`minutes-state.json`), 그 뒤 새로 생긴 회의록만 틱당 `max_per_tick` 개까지 분석한다. 분석과 근거 보기에는
  회의록의 **결론부만** 쓴다(`meeting_minutes.finalized_view` — 부록의 원문 전사본은 빠진다). 결론부는
  `<보드 루트>/minutes/gd-<파일 id>.md`(0600)에 남아 근거 링크 `/source/meeting/gd-<id>` 가 Drive 를 다시 부르지 않는다.
  같은 회의 시리즈(제목에서 날짜·「회의록」·차수를 뺀 것)는 한 업무라 결정 전에는 카드가 하나만 서고 등급도 함께 간다.
  메일과 겹치는 일은 "이미 있는 할 일" 목록으로 걸러진다. 끄려면 `"analyze": {"minutes": false}`.
- `analyze.enabled` 기본 false — 릴리스만으로는 카드가 올라가지 않는다. 켜면 첫 틱은 워터마크를 "지금"으로
  잡기만 하고(과거 메일함 전체를 제안하지 않는다) 그 뒤 새 메일만 본다. 틱당 상한 `max_per_tick`.
- 상태 경로 덮어쓰기: `PROJECT_BOARD_ROOT`, `PROJECT_BOARD_CONFIG`, 회의록 폴더 `PROJECT_BOARD_MEETING_DIR`.
- 과제 목록(카탈로그): `"projects": [{"name": "<과제 이름>", "aliases": ["<별칭>", …], "note": "<한 줄 설명>", "grade": "<기본 보안 등급>"}]`
  (`grade` 는 선택, 없으면 `과제내부` — 아래 「업무 보안 등급」).
  분석은 이 목록에서 **글자 그대로** 하나를 고르고, 맞는 것이 없으면 `미분류` 로 답한다(새 이름을 짓지 않는다).
  실제 과제 이름은 노드 설정 파일에만 둔다 — 코드·저장소에 적지 않는다(「개인화 코드 금지 규칙」).
- 프롬프트 판본: `"analyze": {"prompt": "v3"}`(기본). v2 는 광고·자동 알림·전 직원 일반 공지를 사유와 함께 거르고,
  받는 사람에게 요구된 행동만 할 일로 뽑으며, 대시보드에 이미 열린 할 일과 같은 일은 빼고, 상대 날짜도 계산한다.
  v3 는 v2 에 업무 보안 등급 **제안**을 더한다. `v1`·`v2` 는 비교용으로 남는다.

## 3. 명령

```bash
python3 -m automation.project_board analyze --mail <uid>        # 또는 --meeting <회의록.md>; 카드 게시 + APPROVAL-THREAD 줄
python3 -m automation.project_board revise <제안> --set-due 1=2026-10-24 --set-owner 2=담당자 --drop 3 --add '제목|담당|2026-11-01'
python3 -m automation.project_board proposals                  # 제안과 상태
python3 -m automation.project_board revise <제안> --grade 대외비         # 등급 바꾼 수정 카드(올리기·낮추기 모두 카드로)
python3 -m automation.project_board grade <todo_id> 기관지정            # 승인된 업무의 등급 올리기만(그 업무 할 일 전부)
python3 -m automation.project_board progress <todo_id> --status 완료|진행|보류|열림 [--progress N] [--note 메모]
python3 -m automation.project_board build                      # 대시보드 파일 다시 만들기
python3 -m automation.project_board serve                      # 127.0.0.1:<port> (유닛이 상시 실행)
python3 -m automation.project_board digest [--request-mail]    # 날짜별 스냅샷, 메일은 승인 카드로만
python3 -m automation.project_board dryrun --days 28 --limit 120 --out <체크아웃 밖 경로>.jsonl [--prompt v1|v2|v3]
python3 -m automation.project_board dryrun --minutes 8 --out <체크아웃 밖 경로>.jsonl   # 최근 확정 회의록 8개(읽기 전용)
```

## 테일넷에서 열기 (tailnet 전용, 공개 아님)

서버는 노드의 루프백(`127.0.0.1:<port>`)에만 붙는다. 소유자 기기에서 https 로 열려면 **테일스케일 운영자 권한이 있는
호스트**(게이트웨이)에서 `tailscale serve` 를 쓰고, 그 호스트가 SSH 포워드로 노드 루프백에 닿게 한다. Funnel(공개)은 쓰지 않는다.

1. 노드 설정 `~/.hermes/project-board/config.json` 에 게이트웨이 주소와 허용 로그인을 적는다(값은 설치별, 저장소에 적지 않는다):
   ```json
   {"dashboard": {"tailnet": {"origins": ["https://<게이트웨이>.<tailnet>.ts.net:<port>"], "logins": ["<소유자 로그인>"], "token": false}}}
   ```
   서버는 1시간마다 다시 뜨므로(`RuntimeMaxSec`) 그 안에 반영된다. 즉시 반영하려면 `systemctl --user restart autophagy-project-board`.
2. 게이트웨이에서 노드 루프백으로 가는 상시 포워드(사용자 유닛, `Restart=always`, 사용자 linger 켜기):
   `ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -L 127.0.0.1:<로컬포트>:127.0.0.1:<port> <노드>`
3. 게이트웨이에서 `tailscale serve --bg --https=<port> http://127.0.0.1:<로컬포트>` — `tailscale serve status` 에 `(tailnet only)` 로 보여야 한다. serve 설정은 tailscaled 가 저장해 재부팅 뒤에도 유지된다.
4. 소유자 기기(테일스케일에 소유자 계정으로 로그인)의 브라우저에서 `https://<게이트웨이>.<tailnet>.ts.net:<port>/` 를 연다. 토큰은 묻지 않는다.

규칙: 테일넷 이름으로 들어온 요청이나 `Tailscale-User-Login` 헤더가 붙은 요청은 그 로그인이 `logins` 에 있어야 한다(아니면 403,
로그인이 없어도 403). 그 로그인이 맞으면 **토큰 없이** 열린다 — 소유자 결정(2026-10-14): "토큰 빼기 — 테일스케일 + 형 계정만으로".
남는 위험: `tailscale serve` 는 그 헤더를 호출자의 실제 신원으로 덮어쓰지만, 노드·게이트웨이의 다른 로컬 프로세스는 루프백에
헤더를 위조해 보낼 수 있다(소유자가 받아들인 위험). 다시 막으려면 `"token": true` — 그때는 테일넷에서도 처음 한 번 `?t=<토큰>`
(노드 `~/.hermes/project-board/serve.token`)이 필요하다. 토큰 없이 들어온 TODO 체크(POST)는 설정된 테일넷 출처의 `Origin` 이
**반드시** 붙어 있어야 한다 — 소유자 브라우저에 열린 다른 사이트가 serve 를 거쳐 체크하지 못하게. 테일넷 설정이 없으면 신원 헤더가
붙은 요청은 모두 거부되고, 테일넷이 아닌 루프백 접속(SSH 포워드 등)은 예전처럼 토큰이 필요하다.

보드 DB 는 스키마 판본(`PRAGMA user_version`)을 갖는다. 코드보다 새 판본이면 쓰기 전에 멈추고("run the released code"),
실제 보드(`~/.hermes/project-board/board.db`)의 스키마는 릴리스 런타임(`/srv/autophagy-agent-releases/…`)에서 돈 코드만 바꾼다 —
릴리스 전 코드로 노드에서 시험할 때는 **반드시** `PROJECT_BOARD_ROOT` 를 샌드박스로 둔다(2026-10-14 사고: 드라이런이 실제 보드를
이관해 배포된 코드의 반영 틱이 실패했다). 과제 목록을 읽는 `dryrun`·`status` 는 보드를 읽기 전용으로만 연다.

`dryrun` 은 운영 전 분류 점검용이다 — 최근 받은 메일을 그대로 분석해 결과를 비공개 JSONL(0600) 한 파일에만 쓰고,
제안·카드·프로젝트 데이터·대시보드는 하나도 만들지 않으며 메일함은 읽기만 한다. git 체크아웃 안 경로는 거부한다.

MailOn 런타임의 `data/` 는 배포본에서 공유 상태 디렉터리(`mailon-runtime/state/data`)로 가는 링크다. 원문·첨부
경로는 런타임 루트 또는 그 `data/` 실경로 안일 때만 읽고, 그 밖으로 풀리는 경로는 거부한다.

종료 코드: 0 완료, 2 입력 오류, 3 카드 게시 거부, 4 모델·원천 일시 불가(재시도).

## 업무 보안 등급

등급은 `공개 < 과제내부 < 대외비 < 기관지정` 네 단계이고 단위는 과제가 아니라 **업무**다. 업무 키는 카드가 이미 쓰는
대화 키다 — 메일은 제목에서 Re/Fw 를 뗀 스레드, 회의록은 원본 id. 업무의 등급은 `board.db` 의 `tasks` 표에 한 줄로만
있고 할 일은 그 줄을 읽으므로, 등급을 바꾸면 그 업무의 할 일 전부가 같이 바뀐다(최근 기록에 「보안 등급 변경」).

- 정하는 순서: 이미 승인된 업무면 그 등급을 그대로 쓴다. 처음 보는 업무면 분석의 제안과 과제 기본값(`projects[].grade`,
  없으면 과제내부) 중 **더 엄격한** 쪽이다 — 분석은 기본값보다 느슨하게 만들지 못한다.
- 확정: 카드(판본 `project-proposal-v2`)에 「보안 등급: … — 이 업무의 할 일·이후 카드 전부에 같은 등급」 줄이 실리고 소유자의
  ✅ 가 확정이다. 바꾸려면 `revise --grade` 로 수정 카드를 올린다. `grade` 명령은 승인된 업무를 **올리기만** 한다.
  이미 게시된 `project-proposal-v1` 카드는 그대로이고, 등급 없는 옛 제안은 직렬화가 같아 승인 해시도 그대로다.
- 내보내기: 대시보드는 소유자 화면이라 배지로 보인다. 밖으로 나가는 사본(일일 요약 메일 첨부 `digest`, 이후의 외부 연동)은
  `snapshot(exported=True)` 하나만 쓰며, 대외비·기관지정 할 일·근거·기록·대기 제안과 그것만 가진 과제 이름까지 빼고
  "N건은 이 사본에서 뺐습니다" 만 남긴다. `tests/unit/test_project_board_grade.py` 가 이것을 막는다.
- 내용으로 경로를 고르거나 막지 않는다(2026-10-09 민감 판정 제거 그대로) — 등급은 소유자가 확정한 표지일 뿐 모델 경로를
  바꾸지 않는다.

## 4. 화면

위 메뉴는 **탭**이다 — 누르면 그 화면 하나만 보이고 나머지는 숨는다. 주소 `#summary`·`#projects`·`#todos`·`#schedule`·
`#sources`·`#archive` 가 탭을 기억해 새로고침·뒤로 가기가 그대로 동작하고, 첫 화면은 요약이다. 메일 첨부용 파일도 같은 탭이며
스크립트가 꺼진 메일 뷰어에서는 모든 화면이 위아래로 펼쳐진다(외부 의존 없음). 빈 화면은 "아직 없음 — 자동 분석이 새 메일에서
할 일을 찾고 카드에서 ✅ 하면 여기 나와요" 로 채운다.

요약(지연·이번 주 마감·진행 중·검토 대기 칩, 승인 대기 제안은 데이터와 분리 표시, 최근 기록) · 프로젝트 카드(완료/전체 진척,
지연, 다음 마감 D-day) · 할 일(프로젝트별 체크리스트, 검색·상태 필터) · 일정(지연/이번 주/다음 주/이후/미정) ·
근거(메일 제목·보낸 사람·요약·첨부, 만든 할 일) · 최근 기록. 할 일·근거·대기 제안에 업무 보안 등급 배지가 붙는다
(대외비·기관지정은 「외부 비공개」). 데스크톱과 375px 폭에서 가로 스크롤 없이 읽힌다.

**프로젝트별 보기**(2026-10-15 소유자 지시). 요약과 프로젝트 탭의 프로젝트 카드를 누르면 `#project/<프로젝트 이름>`
화면이 열린다 — 그 프로젝트의 칩(지연·이번 주 마감·완료·검토 대기), 할 일(체크 가능), 일정, 근거(메일·회의록)만 있고
머리글에 그 프로젝트에 있는 보안 등급 배지가 모두 붙으며 행마다 배지도 그대로다. 주소가 곧 그 화면이라 뒤로 가기·
새로고침·주소 공유가 동작하고, 메뉴는 「프로젝트」가 켜진다. 할 일·일정 탭 위에는 「프로젝트」 **드롭다운**(`전체 프로젝트` +
프로젝트들)이 있어 고르면 그 탭이 한 프로젝트로 좁혀진다(`#todos?p=<이름>`·`#schedule?p=<이름>` — 역시 주소로 남는다.
과제가 많아도 버튼이 늘어나지 않게 2026-10-15 소유자 지시로 알약 버튼을 드롭다운으로 바꿨다). 할 일 탭의
검색·상태 필터는 고른 프로젝트 안에서 동작하고 건수도 그 안에서 센다. 프로젝트 화면이나 알약에서 고른 프로젝트는
위 메뉴 「할 일」·「일정」으로 옮겨도 유지되고 드롭다운에서 「전체 프로젝트」를 고르면 풀린다. 할 일 하나는 전체 목록과 프로젝트 화면에 둘 다
보이지만 체크하면 기록 뒤 화면을 다시 불러오므로 두 곳의 상태가 갈라지지 않는다. 없는 이름은 `전체`·`프로젝트` 탭으로 돌아간다.
화면 구성은 `dashboard.py` 하나가 렌더한다.

**프로젝트 순서**. 프로젝트 카드·드롭다운·할 일과 근거의 프로젝트 묶음은 모두 `dashboard.project_sort_key` 한 함수가 정한
순서를 따른다. 지금은 이름(가나다)순이고, 소유자가 말한 「주관 순서」가 정해지면 그 함수만 바꾼다.

**프로젝트 보관**(2026-10-15 소유자 지시). 프로젝트 화면 머리글의 「보관」을 누르면(확인 한 번) 그 프로젝트가 요약·프로젝트·
할 일·일정·근거·최근 기록과 드롭다운에서 사라지고 「보관함」 탭(`#archive`)에만 카드로 남는다. 카드에는 보관 시각과
누가 보관했는지가 붙고, 눌러 들어가면 할 일·일정·근거가
그대로 있으며 「보관 해제」로 되돌린다. **표시만 바꾸고 지우지 않는다** — `board.db` `projects` 행의 `archived_at`·`archived_by`
두 칸(스키마 v3)과 최근 기록의 「보관」·「보관 해제」 한 줄이 전부이고 할 일·근거·등급은 그대로다.

**누가 했는지**. 보관과 할 일 체크는 같은 신원을 남긴다(`server._actor`, 최근 기록의 `events.actor` 칸, 스키마 v3) —
테일넷으로 열면 `tailscale serve` 가 넣은 테일스케일 로그인(평소 경로, v1.27.0 부터 토큰 없이), 노드에서 루프백으로 직접
열면 `노드 로컬 접속(127.0.0.1)` 처럼 접속 주소다. 소유자 화면은 보관함 카드와 최근 기록 줄 끝에 그 신원을 보여 주고,
밖으로 나가는 사본은 싣지 않는다. 그전에 기록된 체크는 신원 칸이 비어 있다. 권한은 할 일 체크와 같다:
`POST /project/<이름>`(`archived=1|0`)은 토큰(쿠키+헤더, 같은 출처) 또는 허용 목록의 테일넷 로그인+테일넷 `Origin` 이 있어야
하고 아니면 401/403 이다. 밖으로 나가는 사본(`digest`)은 보관함과 보관 시각만 싣고 누가 보관했는지는 싣지 않으며, 보관 버튼도
없다. 보관한 프로젝트에 새 카드가 승인되면 할 일은 들어가되 프로젝트는 보관함에 그대로 있고(해제는 소유자가 한다),
놓치지 않게 보관함 안에서만 알린다 — 위 메뉴 「보관함」 옆에 보관한 프로젝트 수와 「새 N」, 보관함 카드에 「보관 뒤 새 할 일 N」.
요약을 포함한 메인 화면에는 보관한 프로젝트가 어떤 형태로도 나오지 않는다(소유자: 메인에서는 싹 다 사라지게).

**되돌리기**. 스키마 v3 이전 판(v1.34 이하)의 코드는 v3 보드를 열지 않는다("newer than this code"). 보통은 앞으로 나가는
릴리스로 고친다. 그래도 옛 판을 돌려야 하면 대시보드 유닛을 멈추고 `board.db` 를 복사해 둔 뒤 아래를 실행한다 — 보관
표시와 기록의 신원만 사라지고 할 일·근거·등급은 남는다(옛 코드가 `projects` 에 칸 네 개로 쓰므로 칸을 지워야 한다,
SQLite 3.35+). `tests/unit/test_project_board_archive.py` 가 이 블록을 그대로 실행해 v2 칸과 같아지는지 확인한다.

```sql
ALTER TABLE projects DROP COLUMN archived_at;
ALTER TABLE projects DROP COLUMN archived_by;
ALTER TABLE events DROP COLUMN actor;
PRAGMA user_version = 2;
```

**목록 접기**(2026-10-15 소유자 지시). 할 일 탭의 프로젝트 묶음, 일정의 지연·이번 주·다음 주·이후·미정 묶음, 근거 탭의
프로젝트 묶음, 프로젝트 화면의 할 일·일정·근거 묶음은 머리(▾/▸)를 누르면 접히고 펼쳐진다. 접혀도 머리에
건수가 남고, 접힘 상태는 브라우저 저장소(`localStorage` 의 `pb-fold:<묶음>`)에 남아 새로고침해도 유지된다 — 기기마다
따로이고 서버는 모른다. 처음에는 모두 펼쳐져 있다. 근거 탭은 이 때문에 프로젝트별로 묶여 보인다.
