# 스킬 제작·배포 가이드 (W1-8)

Hermes 인스턴스(agent/peer)에 올라가는 스킬을 만들고, v2.2 스킬 게이트
(**샌드박스 → 자가승인 → 마운트**)를 통과시켜 배포하는 방법.

## 0. 제작 전 기존 스킬 대조 (필수, 2026-09-05)

**새 스킬을 만들거나 기존 스킬을 확장하기 전에, 전체 기존 스킬 목록과 관련 후보의 `SKILL.md`·
연결 파일을 먼저 읽는다.** 목적은 하나다 — 같은 일을 하는 스킬을 두 벌 만들지 않는 것. 라우팅이
갈리고(같은 요청에 서로 다른 스킬이 뽑힘), 같은 버그를 두 곳에서 고치게 되며, 승인 게이트도 두
벌이 된다. 소유자 지시(2026-09-04, 티켓 `t_0a7959e9`).

### 사람·에이전트가 손으로 만들 때 (체크리스트)

1. **전체 목록을 먼저 연다** — `hermes skills list --plain`(계정 자가 스킬 + `external_dirs` 의
   governed 배포본)과 리포의 `skills/`. 둘 다 본다: 한쪽만 보면 배포본이나 자가 저작물을 놓친다.
2. **후보의 `SKILL.md` 를 실제로 읽는다**(`hermes skills view <name>` 또는 파일 직접). 이름이
   비슷한 것뿐 아니라 **설명 낱말이 겹치는 것**을 후보로 잡고, 그 스킬의 `scripts/` 와
   `tests/unit/test_<name>*.py` 까지 연다.
3. **여덟 항목을 대조한다** — 이름 · 설명 · 트리거(`!cmd`·발화 문구) · 기능 · 입출력 ·
   외부효과 게이트(승인 필요 여부) · 스크립트 · 테스트.
4. **판단 순서는 재사용 → 확장 → 통합 → 신규**다. 기존 스킬이 있으면 **신규 제작보다 그 스킬의
   패치 또는 상위 스킬로의 통합을 먼저** 고른다. 새로 만드는 쪽이 쉬워 보여도, 그것은 이 저장소가
   아니라 다음 사람이 갚는다.
5. **그래도 새로 만들어야 하면** 새 `SKILL.md` 에 `## 기존 스킬 대조` 절을 넣고 두 줄을 남긴다 —
   **차이**(왜 기존 스킬의 확장으로 흡수되지 않는가)와 **재사용 구성요소**(어떤 스크립트·트리거·
   게이트·낱말을 그대로 가져왔는가). 근거가 없으면 그 스킬은 아직 만들 때가 아니다.

### 자동 생성 파이프라인의 기계 게이트

반복 감지기(`automation/skill_generation/`)는 초안을 **쓰기 전에** 같은 대조를 스스로 돌린다
(`precheck.py`, LLM 없이 결정적). 열거 대상은 런타임/리포 `skills/` · governed live 마운트 ·
계정 자가 스킬 루트 셋이고, 점수 정의(`containment` ≥ 0.5 이고 겹친 낱말 ≥ 5)는
`automation/selfskill_audit/overlap.py` 를 그대로 import 한다 — 사후 감사와 제작 전 게이트가
같은 자를 쓴다.

- **판정이 `REUSE-EXISTING`** 이면 초안 디렉터리를 만들지 않고 원장에 그 상태만 적는다. W1-8
  승인 요청도 나가지 않는다. 운영자는 겹친 스킬을 **패치**한다.
- **판정이 `NEW`** 면 초안을 만들되 생성된 `SKILL.md` 안에 `## 기존 스킬 대조` 절(열거 개수,
  가장 가까운 3개와 점수, 차이, 재사용 구성요소)이 함께 들어간다.
- **증적은 판정마다 한 줄** — `~/.hermes/skill-generation/reviews.jsonl` 에 열거한 전체 이름
  (`enumerated`) · 실제로 읽은 `SKILL.md` 경로(`viewed`) · `matches` · `verdict` 가 남는다.
  관측마다가 아니라 **판정 한 건에 한 줄**이다.

```bash
# 그 초안이 무엇과 대조됐는지 다시 꺼내 본다(없으면 exit 1)
python3 ~/.hermes/skill-generation/runtime/automation/skill_generation/cli.py review <auto-이름>
```

`observe` 는 판정이 날 때마다 `PRECHECK <verdict> <name> matches=<겹친 스킬 이름>` 한 줄을 낸다.

### 한계 — 벤더 `skill_manage(create)` 에는 훅이 없다

에이전트가 Hermes 자체 도구로 자가 스킬을 만드는 경로에는 제작 전 훅을 걸 자리가 없다(v0.18.2).
그 경로의 중복 탐지는 여전히 **사후** `automation/selfskill_audit/` 의 겹침 advisory 가 맡는다
(§5 「통제 수단은 승인이 아니라 감사다」). 이 절의 기계 게이트는 반복 감지기가 만드는 자동 제안과
관리자 배포 스킬(§1~§2)에 적용된다.

## 1. 스킬 형식 (agentskills.io)

스킬은 repo `skills/<skill-name>/` 디렉터리 하나다. Hermes는 자기 스킬 루트에
`<skill-name>/` 디렉터리가 있으면 자동 발견한다(`hermes skills list`에
`local/local/enabled`로 표시 — 별도 install 불필요). 관리자 배포본이 사는 루트는
계정 홈이 아니라 `<skill_store>/live`이며, 에이전트 계정은 그것을 Hermes
`skills.external_dirs`로 읽기 전용 발견한다(§5 참조).

```
skills/<skill-name>/
├── SKILL.md            # 필수. frontmatter + 사용법 본문
└── scripts/
    ├── <main>.sh       # 스킬이 부르는 실행물(선택)
    └── scenario.sh     # 필수(배포 파이프라인용). 샌드박스 검증 시나리오
```

`SKILL.md` frontmatter 필수 필드 — 파이프라인 lint가 강제한다:

```yaml
---
name: <skill-name>        # 디렉터리명과 정확히 일치 (^[a-z0-9][a-z0-9-]{1,40}$)
description: "10자 이상의 설명."
version: 1.0.0            # 권장
license: MIT              # 권장
metadata:
  hermes:
    tags: [ ... ]         # 권장
---
```

### 결과 통지 (승인 게이트 스킬 필수 — 2026-08-23)

승인 ✅/⛔ 뒤의 **결과**(실행 완료·취소·만료)는 지시가 온 채널의 스레드로 돌려보낸다 — DM은
승인 전용이다. 새 스킬 체크리스트:

1. mutating CLI에 `--origin-channel-id` / `--origin-message-id`(선택) 인자 → 레코드에
   `origin_channel_id` / `origin_message_id` 저장(승인 해시 바인딩 밖, 레거시 레코드는 부재 허용).
2. 결과 통지는 `automation.interop.origin_notice.deliver(...)` 경유 — 스킬은 자기 Discord `api`
   호출자·청킹 `transport_factory`(`DiscordTransport`)·`fallback`(기존 소유자 통지)만 주입한다.
   자체 스레드 생성 코드는 만들지 않는다. 참조 구현: `origin_notice.deliver`를 부르는 기존 스킬 CLI(`automation.interop.origin_notice` 호출처).
3. 문구는 대상·id·사유를 담고(`✉️ 발송 완료: <제목> → <수신자> (draft <id>)` 꼴), 스킬의 마스킹
   규칙을 따른다(채널에 낼 수 없는 내용은 id만 — calendar 선례; 성립하지 않으면 제외하고 사유 등록).
4. 통지는 best-effort: 실패가 tick·exit code·영수증·원장을 바꾸면 안 된다. E2E·주입 승인은
   `NOTIFY-SKIP`.
5. SKILL.md에 "채널 지시 시 `--origin-*` 전달, 결과는 원 채널 스레드, 승인 요청은 `#agent-chat`의 `승인-<kind>` 스레드(v7)"를 적고,
   RED→GREEN 테스트(origin→스레드 / 없으면 기존 경로 / 스레드 실패→폴백)와 scenario를 갱신한다.

강제: `tests/unit/test_origin_notice_adoption_conformance.py`(승인 producer 스킬의 채택 또는 사유
있는 예외). 원칙 전문은 루트 AGENTS.md 「결과 통지 원채널 스레드 규칙」.

### 승인 요청 답장 링크 (전 스킬 필수 — 2026-09-23)

에이전트가 실행하는 승인 요청 명령은 카드를 게시한 **직후** 승인 스레드 좌표를 한 줄로 낸다. 에이전트
답장은 봉투를 거치지 않으므로, 이 줄이 없으면 "승인 스레드에 게시했다" 가 좌표 없이 나간다.

1. **게시 성공 뒤 한 줄** — 저장 레코드(또는 게시가 돌려준 entry)에서 `approval_guild_id`·
   `approval_thread_id` 를 담은 매핑을 만들어 `automation.interop.thread_pointer.approval_thread_line(
   "<키>", <값>, 매핑)` 을 `print` 한다. 키는 그 CLI 가 이미 출력하는 식별자 이름을 쓴다(mail·calendar·
   budget·coordination=`draft`, todo=`hash`). 게시하지 않은 경로(`--no-post`·`posted=0`)는 줄을 내지 않는다.
2. **import 는 감싼다** — `except ImportError` 면 `APPROVAL-THREAD-UNAVAILABLE <키>=<값> err=<타입>` 을
   stderr 에 남기고 끝낸다. 승인은 이미 게시됐으므로 exit code 를 바꾸지 않는다. 형식 문자열을 스킬에
   복사하지 않는다(conformance 가 사본을 RED 로 만든다).
3. **SKILL.md 에 답장 지시** — `url=` 값은 `[승인스레드](<https://example.test/thread>)` 형태의 마스킹 링크다.
   Discord가 보관된 스레드를 「알 수 없음」으로 표시하지 않도록 문구와 괄호까지 그대로 전달한다.
   "소유자에게 게시했다고 답할 때 `APPROVAL-THREAD` 줄의 `url=` 값을 그대로
   붙인다. `url=unavailable search=<값>` 이면 링크를 지어내지 말고 그 값으로 검색하라고 적는다." 를 명령
   설명 옆에 둔다.
4. **원장에 등록** — 새 생산자는 `tests/unit/approval_conformance_inventory.APPROVAL_PRODUCERS` 에 오르고
   (lifecycle conformance 가 강제), 그 키를 `tests/unit/test_approval_thread_pointer_conformance.py` 의
   `_ADOPTED`(채택 파일 경로) 또는 `_EXEMPT`(사유)에 넣는다. 좌표조차 낼 수 없는 마스킹 스킬(위키·
   patent-prep)과 에이전트 답장이 없는 워처·공급망 경로가 면제 대상이다.

참조 구현: `skills/todo/scripts/todo_cli.py` `_print_thread_line`. 불변식은 루트 AGENTS.md 「승인 요청 답장 링크 규칙」.

### 승인 경로 완결 (전 스킬 필수 — 2026-10-07)

게이트 대상 외부효과를 내는 스킬은 세 조각을 한 사이클에 함께 만든다. 하나라도 빠지면 에이전트가 즉석으로 만들어 보려다가 "이 메시지에 ✅" 를 쓰게 된다(2026-10-07 Obsidian 사건).

1. **요청 명령(카드 생산자)** — 에이전트가 부르는 CLI 가 본문을 동결하고 공용 `approval_lifecycle.request_owner_approval` 로 카드 하나를 게시한다. 카드는 외부효과 게이트가 계산하는 같은 `action_hash` 에 묶고, 게시 직후 `APPROVAL-THREAD` 줄을 낸다. 참조 구현: `automation/obsidian_write/note_request_cli.py`.
2. **✅ 워처** — 리액션만 폴링하는 no-agent cron(또는 systemd 유닛)이 소유자의 비봇 ✅ 를 읽고(⛔ 우선), 승인 기록을 게이트 원장에 전사한 뒤 동결된 본문 그대로 실행한다. 배포는 `deploy-manifest.txt` 의 `v2:cron` 행으로 선언한다.
3. **영수증** — 실행 뒤 원격에서 다시 읽어 확인하고, 결과를 `origin_notice.deliver(..., outcome=...)` 로 요청 스레드에 남긴다.
4. **원장 두 곳에 등록** — `tests/unit/test_gated_effect_paths_conformance.py` 의 `GATED_RULES`(새 denylist 규칙 → 생산자)와 `PRODUCER_WATCHERS`(생산자 → `cron:<이름>`·`systemd:<경로>`·`manual:<사유>` + 테스트 파일)다. 빠지면 빌드가 RED 다.
5. **SKILL.md** — 요청 명령과 `APPROVAL-THREAD` 링크 답장만 안내한다. 소유자에게 채팅 메시지에 ✅ 를 누르거나 `실행 <id>` 를 답하라고 요청하는 문구를 쓰지 않는다. 전용 요청 명령이 없는 작업은 공용 `python3 -m automation.effect_request request drive-save|command` 로 카드를 올리게 한다 — "승인 경로가 없다"로 끝내지 않는다(2026-10-17 「모든 요청 승인 경로 규칙」, 런타임 가드 `chat_approval_guard` 가 어긴 답장을 바꾼다).

### 소유자 메시지 계약 (전 스킬 필수 — 2026-09-09)

소유자에게 갈 문구는 스킬이 조립하지 않는다 — `automation.interop.owner_message` 의 봉투를 채우고
렌더는 파사드에 맡긴다. **위치가 필드라서** "스레드에 올렸다" 가 좌표 없이 나갈 수 없다. 새 스킬
체크리스트:

1. **봉투 채우기** — `OwnerMessage(subject_key=…, subject=…, fact=…, location=…, owner=Action(…),
   agent_next=…, recovery=…, detail=…)`: 5필드 + kind 상세(`Approval`/`Result`/`Periodic`). 값은 스킬이
   **이미 마스킹한 것**만 옮기고 새로 만들지 않는다. 조치가 없으면 `Action(verb="none")`, 후속 실행이
   없으면 `agent_next=None`(렌더러가 "조치 없음"·"추가 실행 없음" 으로 명시한다), 되돌리기는
   `"not_applicable"`/`"irreversible"` 또는 `Action`. 필드를 늘리지 않는다(5필드 상한).
   **신규 승인 카드에는 `render_version="owner-ko-v2"`를 명시**한다. 다섯 필드는 데이터 계약이며
   화면의 다섯 줄을 뜻하지 않는다. v2의 `fact`는 항목별 줄바꿈을 보존하고 인용 블록으로 표시한다.
   제목에 긴 키를 넣지 않는다(`subject_key`는 8자 하단 참조로 표시). `Approval.expires_at`은
   자기 시간대를 보존한 `YYYY-MM-DD HH:MM (+09:00)` 형식으로 보이고, 위치가 자기 메시지/같은
   채널/해당 없음이면 위치 줄을 생략한다. 비지역 링크·검색 안내는 남는다. 해당 없는 되돌리기만
   생략하며 취소 효과와 다음 실행은 계속 표시한다.
2. **`Ref` 만들기** — 위치는 문장이 아니라 좌표다. 승인 카드 좌표는
   `automation.interop.origin_notice.approval_location(record, search=(라벨, 키))` 이 레코드의
   `approval_guild_id`/`approval_thread_id`/`message_id` 에서 만들어 준다(직접 조립 금지). 길드를 모르면
   `space="unknown"` 으로 두고 `search` 를 실어 **링크 대신 검색 안내**가 나가게 한다 — `@me` 로 DM
   링크를 찍지 않는다. 위치가 없는 통지는 `Ref(scope="none")`, 카드가 자기를 가리키면 `Ref(scope="self")`.
3. **파사드로 보내기(목적지가 바뀌면 재렌더)** — 결과 통지는
   `origin_notice.deliver(..., content=…, message=envelope, fallback_destination=…)`, 정기 통지는
   `owner_notice.notify_owner(content, message=envelope)` / `notify_owner_dm(...)`. 파사드가 **실제
   목적지마다** 다시 렌더하므로 스킬은 문자열을 두 번 만들지 않는다. 봉투 import 는 `except ImportError`
   로 감싸 실패 시 `None`(=기존 `content` 경로)을 돌려주고, 호출은 능력 프로브
   `getattr(origin_notice, "ACCEPTS_OWNER_MESSAGE", False)` 뒤에서만 한다 — 옛 런타임이 `message=` 를
   `TypeError` 로 거부하면 그게 곧 통지 유실이다. `content` 만 넘기는 능력 폴백 호출이 채택으로
   인정되려면 **같은 최내부 스코프** 안에 **같은 파사드로 해석되는** `message=` 호출이 있고,
   두 호출의 **content 표현식 AST(`ast.dump`)가 같아야** 한다. 서로 다른 파사드끼리는 짝이
   아니며, 본문 없는 호출도 짝이 아니다(`deliver` 는 `content=`, `notify_owner`·`notify_owner_dm` 은
   첫 위치 인자 또는 그것이 없을 때 `content=` 를 비교한다). 이는 문법적 짝 검사이지 능력 프로브의
   분기 동작 증명은 아니다. 승인 카드는 파사드가 아니라 **생산자별 등록 렌더 루트에서 도달하는 경로**로
   `render(message, destination=Ref(scope="self"))` 를 부른다(카드 자신이 목적지다). 채택 검사는
   `_CARD_RENDER_ROOTS` 에 등록된 루트의 **자기 모듈**에서 시작한다. 루트 스코프 자체 또는 그 루트가
   참조하는 같은 모듈 함수 경로에 `owner_message` 에서 import 한 `render`(별칭·`module_alias.render`
   포함) **호출**이 있어야 한다. 버전 디스패치 테이블을 통한 참조도 인정하지만, import 만 하거나
   루트에서 도달하지 않는 형제 렌더러가 있는 것만으로는 채택이 아니다. 참조 구현:
   `automation/repair/repair_approval_render.py` `_render_v3`(카드).
4. **마스킹 우선순위** — 스킬의 마스킹 규칙이 링크 규칙을 **이긴다**. 채널에 낼 수 없는 내용은 `fact`
   에서 빼고, 좌표조차 낼 수 없으면 위치를 싣지 않는다(위키 본문·특허 반출=`scope="none"`, calendar
   류=draft id 만). 링크를 넣으려고 마스킹을 풀지 않으며, 제외한 사유는 5번 원장에 적는다.
5. **원장 등록** — `tests/unit/test_owner_message_adoption_conformance.py` 에 자기 자리를 만든다: 승인 카드
   생산자는 `_CARD_RENDER_ROOTS` 에 `<생산자 scope>` → `<렌더 루트 scope>` 한 줄(렌더 경로를 다른
   모듈로 옮기면 **같은 커밋에서** 그 줄을 고친다). 이관 원장 `_RAW_CONTENT_EXEMPT` 는 비었고 빈 상태를
   가드한다 — 새 발신자는 바로 봉투를 채택한다. 실제 구조적 경계는 `_PERMANENT_RAW_CONTENT_EXEMPT`
   에 사유와 함께 등록한다. 현재는 최소정보 리마인더, 자체 카드 없는 Obsidian 위임, budget·calendar의
   문자열 수신 경계다. 문자열 수신자는 이미 렌더된 본문·기존 런타임 폴백을 받아 재렌더하지 않는다.
   이관하지 않은 줄을 지우지 말고 **같은 커밋에서** 이관하거나 사유 있는 영구 예외로 승격한다.
   `automation` import 가 불가능해 URL 을 직접 조립하는 파일은 `_LINK_LITERAL_ALLOWED` 에, 소유자 대면이
   아닌 전송 내부·피어 프로토콜은 `_NOT_OWNER_FACING` 에 적는다. `*_not_stale` 가드와
   `test_ledgers_have_reasons_when_registered` 가 각각 낡은 줄과 빈 사유를 RED 로 만든다.

**문자열 경로는 유지(RETAINED)**: 영구 예외와 능력 폴백이 남아 `deliver`·`notify_owner`·`notify_owner_dm`의
`content: str` 을 제거·개명하지 않는다. meeting 게이트웨이는 INTEROP_RUNTIME을 보장받지 못해 별도
문자열 ACK를 쓰며 `_THREAD_API_ALLOWED` 와 `test_meeting_runtime_root` 가 그 경계를 지킨다.
모든 경계·폴백을 대체해 예외가 해소되고 격리 meeting 배달을 검증한 뒤에만 퇴역을 재판정한다.

강제: `tests/unit/test_owner_message_adoption_conformance.py`(AST 인벤토리 + 사유 있는 원장). 원칙 전문은 루트
AGENTS.md 「소유자 메시지 계약 규칙」.

**형 채널 글에는 기계 출력이 없다(2026-10-20)**: no-agent 작업의 stdout 은 곧 형 채널 글이다 — 사람 말 한두 줄
(무엇이 됐나)과 링크, 형 할 일이 있으면 그것만 쓴다. 자식 CLI 의 결과 JSON·`KEY-FAIL code=…` 같은 표식은 stdout 에
쓰지 않고 stderr(내부 로그)로 보낸다(`subprocess.run(..., stdout=PIPE)` 로 잡아 넘긴다 — 선례
`skills/meeting/scripts/meeting_pending_transcript_watch.py`). 그래도 섞여 나오면 출구(`cron_timer_run.deliver`,
`owner_notice.notify_owner`)가 `automation/interop/owner_text.py` 판정으로 JSON 줄은 빼고 진단 줄은 페어 채널로
돌린다. 새 표식 모양을 만들면 `tests/unit/test_owner_text.py` 의 표본에 넣는다.

**페어 채널 글은 한 줄이다(2026-10-20 Q304)**: `notify_owner(..., fault=True)` 와 진단 때문에 페어로 옮겨진 봉투는
`owner_message.render_report` 가 머리·칸 없이 "<사실 첫 문장>. 확인할 곳은 <링크·검색 키>, 남은 일은 <할 일>." 로 만든다.
그러니 `fact` 는 `KEY-CODE:` 접두사나 `라벨: 값; 라벨: 값` 나열 없이 혼자 읽히는 문장으로 쓰고, 남은 일은
`Action.argument`(형 조치) 또는 `agent_next` 에 적는다. 형 채널 판본은 그대로다. 강제 `tests/unit/test_pair_report_shape.py`.

**판본 이관은 append-only**: 봉투 `owner-ko-v1`과 이미 게시된 생산자 카드의 판본은 바꾸지 않는다.
생산자에 새 카드 판본을 추가하고 신규 요청에서만 선택한다. 공용 `approval_card.prepare`는 신규
v3을 먼저 선택하며 저장 판본은 그대로 재생한다. 캘린더는 자체 v4를 엄격히 선택해 상세 없는 카드로
강등하지 않는다. 릴리스는 v5다. 전체 카드 길이는 생산자의 기존 최종 한도에서 거부하며 해시 줄을
자르거나 승인 정보를 생략해서 맞추지 않는다. 위키의 신규 판본은 `wiki_gate.py` 동결 해제 전까지
추가하지 않는다. 결과·정기 통지는 명시적 v2를 지원하되 파사드가 v1 봉투를 자동 변환하지 않는다.

### scenario.sh 계약 (샌드박스 필수 통과 조건)

- 파이프라인이 `env -i HOME=… PATH=/usr/bin:/bin AUTOPHAGY_DEMO_SECRET=DUMMY-…`
  환경에서 실행한다. **실시크릿은 절대 주입되지 않는다.**
- 시나리오는 자기 시크릿이 `DUMMY-` 접두사인지 스스로 확인하고, 실토큰
  모양(`sk-`, `ghp_`, `Bot `)이면 즉시 실패해야 한다. 배포 리뷰의 secret-scan은 `sk-…`, `ghp_…`, `Bot|Bearer + 8자 이상 토큰형 문자열`, PRIVATE KEY 블록을 차단한다. **주석/문서 문자열에도 `bot ` + 단어 조합을 피하라** — 실제 사례: `# Discord bot attachment ceiling` 주석이 오탐으로 배포를 막았다(리워드로 해결). 스캐너는 숫자/점 포함 토큰만 매치하도록 개선됐지만 원칙적으로 토큰 모양 문자열 자체를 쓰지 말 것.
- 성공 시 stdout에 `SCENARIO-PASS` 마커를 출력하고 exit 0. 그 외 전부 실패.
- 파이프라인은 `AUTOPHAGY_SKILL_LIVE_ROOT=<peer 홈>/.hermes/skills` 도 준다 — 스테이징 사본은 live 마운트가
  아니라 실행 사본 가드(`skill_mount.governed_copy_refusal`)가 막으므로, 샌드박스가 자기 사본 루트를
  live 로 선언한다(2026-09-03 까지 빠져 있어 v1.1.0 의 가드 채택 스킬 13개가 stage 1 에서 전부 막혔다).
  시나리오가 자기 CLI 를 다시 `env -i` 로 돌리면 이 변수를 **반드시 넘긴다**
  (`AUTOPHAGY_SKILL_LIVE_ROOT="${AUTOPHAGY_SKILL_LIVE_ROOT:-}"`) — `tests/unit/test_governed_copy_guard_conformance.py`
  가 전 governed 스킬에 강제한다.
- heredoc·보조 파이썬은 **`scripts` 디렉터리에서 직접 import** 한다(`sys.path.insert(0, "$script_dir")`,
  `import <module>`). `from skills.<name>.scripts import …` 는 샌드박스에서만 우연히 통과하고(peer
  `~/.hermes/skills` 가 네임스페이스 패키지) live 마운트(`/srv/autophagy-skills/releases/<name>/<sha>`) 위에는
  `skills` 패키지가 없어 post-mount smoke 가 `ModuleNotFoundError` 로 죽는다.
  `tests/unit/test_scenario_deployed_layout.py` 가 그 레이아웃(심링크 팜 + 빈 cwd)에서 시나리오를 돌린다.
- 참조 구현: `skills/hello-autophagy/scripts/scenario.sh`.

### 편집기 BasedPyright 설정

루트 `pyrightconfig.json`은 각 `skills/*/scripts`를 실행 환경으로 선언해, 그 디렉터리가 런타임 `sys.path`에 있을 때 유효한 `import <sibling>`을 편집기가 상대 import 오류로 오인하지 않게 한다. 이는 루트 매니페스트가 없다는 메인 트리 규약의 승인된 **편집기 전용 예외**이며, 패키징·런타임 `sys.path`·CI 검사 동작은 바꾸지 않는다.

#### peer와 같은 격리 조건으로 로컬 재현

리포 안에서 `bash skills/<name>/scripts/scenario.sh`만 실행하면
`AUTOPHAGY_REPO_ROOT`의 기본값이 현재 리포를 가리켜, 실제 peer 검토에서는 없는 공유 모듈을
lazy import할 수 있다. 로컬 PASS와 peer FAIL이 갈리는 것을 막으려면 스킬을 체크아웃 밖으로
복사하고 최소 환경으로 실행한다.

```bash
rm -rf /tmp/isolated
mkdir -p /tmp/isolated
cp -r skills/<name> /tmp/isolated/
tmp_home="$(mktemp -d)"
(
  cd /tmp/isolated/<name>
  env -i HOME="$tmp_home" PATH=/usr/bin:/bin AUTOPHAGY_SKILL_LIVE_ROOT=/tmp/isolated \
    AUTOPHAGY_DEMO_SECRET=DUMMY-skill-review bash scripts/scenario.sh
)
```

이 절차는 `automation/skill_review.py`가 peer 검토에서 만드는 조건을 재현한다. 임의로
`AUTOPHAGY_REPO_ROOT`나 `PYTHONPATH`를 추가하면 격리 검사가 아니므로 결과를 배포 판정에 쓰지 않는다
(`AUTOPHAGY_SKILL_LIVE_ROOT` 는 예외 — 파이프라인이 주는 값이다).

## 2. 배포 파이프라인

```bash
automation/deploy-skill.sh <skill-name>            # 전체 파이프라인
automation/deploy-skill.sh <skill-name> --sandbox-only   # ① 샌드박스만
automation/deploy-skill.sh <skill-name> --request-only [--fresh]  # ①+② 요청 게시까지
automation/deploy-skill.sh <skill-name> --remove   # agent+peer에서 제거
```

- 기본은 로컬(오케스트레이터 머신)에서 실행하며 `DEPLOY_SSH_HOST`
  (`<primary-node>`)로 SSH + `sudo -n -u agent|peer` 한다. 노드 위에서 직접 실행하면
  SSH 없이 동작한다.
- **① 샌드박스(peer)**: 런타임 parse(peer의 hermes CPython = py3.11, cron 인터프리터) →
  lint → hermes 디스커버리 → DUMMY 시크릿 시나리오 → 격리 프로브. 실패 = exit 2, 승인 단계 미진입.
  런타임 parse는 3.12 전용 문법(PEP701 f-string·PEP695 `type` 별칭)이 dev/CI(py3.12)를 통과하고도
  prod(py3.11)에서 SyntaxError로 워처를 죽이는 것을 배포 전에 차단한다(사고 t_90a2e810: triage_gate.py가
  mail 승인 워처를 멈춤). dev 쌍둥이 검사: `tests/unit/test_py311_syntax_guard.py`.
- **② 승인(개인 서버의 #approvals, 소유자 전용)**: agent 봇이 승인 요청을 게시한다.
  **cha 본인 계정의 ✅ 리액션만** 승인으로 인정된다(봇·타인 리액션 거부).
  아직 아무도 답하지 않았으면 **exit 1**, cha가 **⛔로 취소**했으면 **exit 8**이며 어느 쪽도 마운트되지 않는다.
  둘을 나누는 이유는 exit 1이 peer 증명 refresh 재시도를 유발하기 때문이다 — 취소된 배포를 다시 증명하는 것은
  왕복 낭비이고, 로그가 "소유자가 멈춘 뒤에도 파이프라인이 계속 밀어붙이는" 것처럼 읽힌다.
  ⛔는 ✅보다 **우선**한다(둘 다 눌렸으면 취소). **스킬 하나에 살아 있는 승인 요청은 항상 1건**이다 —
  같은 내용(hash)으로 재실행하면 기존 요청 메시지를 그대로 재사용하고(nonce도 유지),
  내용이 바뀌면 옛 메시지를 **먼저 지운 뒤** 새로 올린다(고아 메시지 없음).
  `--fresh`도 같은 규칙을 따른다 — 우회가 아니라 교체(supersede)다.
  기존 요청을 건드릴 수 없는 상황(cha가 이미 ✅/⛔를 눌렀거나, 본문 바인딩 불일치,
  pending 레코드 손상, Discord 조회 실패)에서는 **exit 6**으로 거부하고
  stderr에 `reason=<토큰>`을 남긴다 — 기존 승인 메시지는 그대로 살아 있다.
  승인 성공은 `/srv/autophagy-agents/logs/approvals.jsonl`에 기록된다.
  **소유자의 ✅ 결정은 경과 시간만으로 만료되지 않는다.** peer 증명만 자기 게시 시각부터
  30분(`peer_attestation.PEER_ATTESTATION_TTL`) 유효하며, 배포 시 증명만 만료됐으면 같은
  content hash·nonce·action·destination으로 peer 검증을 다시 수행하고 owner 요청은 재게시하지 않는다.
  본문/바인딩 변경, ✅ 철회, ⛔ 취소, supersede, nonce 재사용은 refresh 전에 fail-closed 차단한다.
  요청 뒤 `skills/<name>/**`를 바꾸면 digest가 달라져 기존 승인을 쓸 수 없으므로 코드를 굳힌 뒤 요청한다.
  운영 노드에서는 1시간 동안 답이 없으면 같은 `autophagy-supply-chain-watch` 틱이 `#approvals`에
  요청 유형·경과시간·원 승인 메시지 점프 링크만 담은 리마인더를 보낸다. 이후에도 미응답이면
  원 게시 시각 기준 매시간 한 번씩 보낸다. 리마인더는 새 승인 요청이 아니므로 링크를 눌러
  **원 메시지**에 ✅/⛔를 남긴다. 전송 실패는 배포 재개 판정을 바꾸지 않고, 실패한 시간 구간은
  중복 방지를 위해 다시 보내지 않으며 다음 시간 구간부터 재시도한다.
- **③ 마운트(agent)**: 복사 → 디스커버리 확인 → invoke 스모크 → peer 샌드박스
  복사본 정리.

### `SELF-SKILL-COLLISION-BLOCK` (exit 4) — 자가 저작물과 이름이 겹칠 때

파이프라인은 stage 1 앞에서 agent·peer 두 스킬 루트를 조사해, 배포하려는 이름이 그
계정의 **자가 저작 스킬**로 이미 존재하면 아무것도 스테이징하지 않고 exit 4로 멈춘다.
우선순위는 없다 — 관리형 스킬 이름 충돌과 같은 원칙이다.

```
SELF-SKILL-COLLISION-BLOCK: <skill> already exists as a self-authored skill on <account> (...)
```

해결(둘 중 하나를 소유자가 고른다):

1. 자가 저작물을 물러나게 한다 — 그 계정에서 `hermes curator archive <skill>`. 원장에
   `archived` 델타로 남으므로 되돌릴 수 있다(`hermes curator restore`).
2. 배포 쪽 이름을 바꾼다 — `skills/<새-이름>/`으로 옮겨 커밋·푸시한 뒤 다시 배포한다.

`--remove`는 이 가드의 대상이 아니다. 충돌에서 빠져나오는 길 자체이기 때문이다.
읽지 못하거나 분류가 모호한 루트(ssh·sudo 거부, `.usage.json` 파싱 실패)도 같은 코드로
멈춘다 — 확인할 수 없으면 남의 작업 위에 마운트하지 않는다(fail-closed).

### ✅ 한 번이면 마운트까지 간다 — 스킬을 새로 만들어도 자동으로 포함된다

위 ②에서 요청만 올려두면(`--request-only`) **소유자가 `#approvals`에서 ✅ 한 번**만 눌러도 마운트까지
끝난다. 세션이 다시 개입하지 않는다 — `autophagy-supply-chain-watch.timer`(2분 주기, 시스템 유닛)가
대기 레코드를 열거해 소유자 결정만 읽고, 승인된 것만 **③을 재개**한다. 상세: [소개](../기능소개/승인-한번-자동배포.md).

**새로 만든 스킬도 등록 없이 자동 포함된다.** 워처의 대상 판정은 스킬 이름이 아니라 승인 종류다 —
`supply_chain_plan.SUPPORTED_KINDS = {"skill-deploy"}`. `deploy-skill.sh`가 올리는 모든 스킬 배포
요청은 이 종류이므로, 스킬 목록이나 화이트리스트를 손볼 필요가 없다.

제외되는 것은 **재개에 필요한 인자가 레코드에 없는 종류**뿐이다 — `managed-activate`(격리 디렉터리
경로가 레코드에 없음) · `skill-publish`(다른 프로그램과 `--managed-repo` 필요). 이들은 추측 실행이
공급망 위험이므로 의도적으로 `retain (unsupported-kind)`로 남겨 사람이 끝낸다.

**재개가 실패하면 유예된다 — 그러나 되돌아온다.** 재개가 실패하면(`failed (resume-exit:N)`) 워처는
같은 실패를 매 tick 반복하지 않으려고 그 요청을 유예한다. 유예는 영구가 아니다 — 실패 지문이
`릴리스 sha:사유`이므로, **원인을 고쳐 랜딩해 노드 릴리스가 바뀌면 다음 tick에 자동으로 재시도된다**
(사람이 다시 부를 필요 없음). 같은 릴리스에서 기다리는 동안에도 **매 tick 한 줄이 남는다** —
`[supply-chain-watch] skill-deploy:<skill> backoff (attempt N, retry in Ns)`. 전에는 이 줄이 없어
유예된 요청이 삭제된 것처럼 보였다(2026-08-04, 8 tick 연속 3건이 로그에서 통째로 누락).

그래도 **급하면 기다리지 않아도 된다** — 같은 릴리스에서 대기 중이거나 수렴을 기다릴 여유가 없으면
아래로 상태를 확인하고 `automation/deploy-skill.sh <skill>`을 직접 한 번 돌린다(승인은 이미 있으므로
③만 수행된다).

```bash
# 무엇이 아직 대기 중인가
ssh <primary-node> 'sudo -n -u agent bash -c "ls ~/.hermes/skill-gate/pending/"'
# 워처가 그 요청을 어떻게 판정했나 (done / retain / failed)
ssh <primary-node> 'journalctl -u autophagy-supply-chain-watch.service -n 30 --no-pager | grep supply-chain-watch'
```

### 무인 회귀 (E2E)

```bash
E2E_TEST_MODE=1 automation/deploy-skill.sh <skill-name>
```

W1-6 injection adapter의 HMAC 서명 승인 레코드를 게이트가 검증한다
(서명 + owner id + 채널/텍스트 일치). **프로덕션 agent gateway에는
E2E_TEST_MODE를 절대 설정하지 말 것** — unit의 production guard가 부팅을
거부한다. 회귀 실행별 시크릿은 agent 홈에서 생성 후 즉시 삭제된다.

### 자동 생성 제안 상한 (크로스커팅 제약 4)

자동 생성 스킬 제안은 `SKILL_PROPOSAL_SOURCE=auto`로 요청해야 하며, 게이트가
ISO 주 기준 **주 3회**를 초과하면 exit 3으로 거부한다(수동 배포는 무제한,
기록은 동일하게 남음).
exit 3은 오직 이 상한에만 쓰인다 — 승인 생명주기 거부는 exit 6이다.

## 4. 관리형 스킬 발행

관리자(cha)가 발행하는 관리형 스킬은 별도의 `managed-skills` 저장소를 통해 배포됩니다.

### 작성 규칙
*   **이름**: 소스 디렉터리명, `SKILL.md`의 `name`, 매니페스트의 `skill` 필드, 그리고 최종 라이브 심링크 이름이 모두 일치해야 하며, 반드시 `managed-` 접두사를 포함해야 합니다.
*   **제약**: 전체 이름은 `^managed-[a-z0-9][a-z0-9-]*$` 패턴을 따라야 하며 최대 41자입니다.

### 발행 파이프라인 순서
1.  **배포 승인 증거 확보**: `deploy-skill.sh <skill> --approve-only`를 실행하여 샌드박스 및 리뷰를 통과하고 소유자 승인을 받은 증거(message_id:nonce)를 얻습니다. 승인 뒤에는 스킬 파일을 수정하지 않습니다. peer 증명만 만료되면 다음 실행이 같은 바인딩으로 자동 재검증합니다.
2.  **발행 요청**: `publish_cli.py`를 사용하여 매니페스트를 생성하고 발행 승인을 요청합니다.
3.  **소유자 승인**: `#approvals` 채널에서 발행 요청에 ✅ 리액션합니다.
4.  **태그 및 푸시**: 승인 확인 후 `publish_cli.py`가 자동으로 SSH 서명된 태그를 생성하고 저장소에 푸시합니다.

## 5. 에이전트 자가 스킬과의 공존 (SS-1, 2026-08-15)

이 가이드가 설명하는 4단계 게이트는 **관리자(cha)가 배포하는 스킬**만 다룬다. 에이전트가
스스로 지은 스킬은 다른 공간에 살고 다른 방식으로 통제된다.

### 루트가 반전됐다

| 루트 | 소유·권한 | 내용 | Hermes에서의 역할 |
|------|-----------|------|-------------------|
| `<계정 홈>/.hermes/skills` | 계정 소유 0700 (쓰기 가능) | 자가 저작 스킬 + Hermes 자기 상태(`.usage.json`·`.curator_state`·`.archive`·`.hub`) | **1차 루트** |
| `<skill_store>/live` | root 소유 read-only | 관리자 배포 스킬(내용 해시 심링크 팜) | `skills.external_dirs` |

예전에는 반대였다 — 계정의 스킬 루트가 live 스토어의 read-only bind mount였다. 그래서
Hermes가 1차 루트에 써야 하는 것을 하나도 쓸 수 없었고(EROFS), Hermes v0.18.2의
`skill_manage(create)`는 **1차 루트에만** 쓰기 때문에 자가 저작이 구조적으로 불가능했다.
반전이 공식 경로인 이유가 그것이다. 탐색 순서는 1차 루트 → `external_dirs` 선언 순이고,
프롬프트 인덱스는 local-first로 중복을 건너뛴다.

반전의 부수 이득이 하나 더 있다: Hermes의 background review·curator는
**configured-external 스킬을 건드리지 않는다**. 관리자 배포본을 external로 등록하면
curator가 그것을 stale로 판정하거나 아카이브할 길이 없어진다.

### 이름 충돌은 양방향으로 막는다

- **self → governed** (자가 스킬이 배포 이름을 선점): Hermes가 막는다.
  ~~`skill_manage(create)`는 **어느 루트든** 같은 이름이 있으면 거부하며~~ **(2026-08-16 반증 — governed 루트가 심링크 팜이라 그 검사가 한 건도 못 본다; 자가 스킬이 배포본을 가릴 수 있고 `selfskill_audit`의 `SHADOWS-GOVERNED` 탐지로만 잡힌다)**, `skill_view`도
  중복 이름을 거부한다(v0.18.2 실측).
- **governed → self** (배포가 자가 저작물을 덮어씀): `deploy-skill.sh`가 막는다 —
  위 §2 `SELF-SKILL-COLLISION-BLOCK`.

### 통제 수단은 승인이 아니라 감사다

소유자 결정(2026-08-15)은 **자유 저작 + 사후 감사**다. 쓰기마다 ✅를 요구하지 않는다
(`skills.write_approval`은 기본값 false 유지, `skills.guard_agent_created: true`로 위험
패턴 스캔만 켠다). 대신 셋으로 통제한다.

1. **격리** — 자가 스킬은 자기 계정 루트에만 착지하고, 관리자 배포본은 read-only external에
   남는다. 배포 판정은 여전히 `readlink <skill_store>/live/<name>`이다.
2. **감사 원장** — `automation/selfskill_audit/`이 계정 루트와 `.archive`를 콘텐츠 해시로
   스캔해 created/edited/archived/restored/removed 델타를 append-only 원장에 적고, 미보고분만
   마스킹 요약으로 소유자에게 DM한다(전송 실패 시 watermark를 전진시키지 않는다).
3. **회수** — `hermes curator archive <name>`으로 물러나게 하고, 죽지 않아야 하는 것은
   `hermes curator pin <name>`으로 고정한다. 실측 시점에 peer의 현역 자가 스킬 2개가
   pin 대상이다.

원장이 승인 게이트가 아님을 분명히 해둔다 — 그것은 **이미 일어난 일**을 소유자에게
보이게 만드는 장치다. 승인 게이트가 필요한 종류의 변경이라면 그것은 자가 스킬이 아니라
`skills/`에 착지해 4단계 게이트를 타야 한다.
