# 헬스체크 릴리스 관측성

## 무엇을

헬스체크가 배포 미러 상태와 독립적으로 현재 릴리스 세대를 `origin/main`과 대조하고,
root 권한으로 설치된 릴리스 헬퍼 두 파일이 불변 릴리스 원본과 같은지도 확인한다. 수리 티켓
명령은 단일 builder가 만들며, 15개 체크의 SSH allowlist 원문 manifest를 함께 제공한다.

## 왜

기존 `release-stale` 탐지는 미러가 뒤처졌을 때만 실행되어, 미러만 먼저 당겨진 상태에서는
낡은 프로덕션 릴리스를 놓칠 수 있었다. 또한 root 헬퍼가 릴리스보다 낡아도 수렴 시점까지
발견되지 않았고, 체크 이름이 포함된 수리 명령 15개는 코드와 allowlist가 쉽게 어긋났다.
새 프로브와 byte-exact manifest 대조가 이 세 관측 공백을 닫는다.

## 사용 시나리오

- **정상**: 릴리스 세대가 origin/main과 같고 설치 헬퍼 해시도 릴리스 원본과 같으면 두
  로컬 체크가 PASS한다. `healthcheck_allowlist_manifest.sh --print`는 D1 형태 명령 15줄을
  출력하며 실제 `report_repair()` 경로와 바이트 단위로 일치한다.
- **드리프트**: 헬퍼가 다르면 해당 체크가 FAIL하고, 파일이 없거나 읽을 수 없으면
  `HELPER-DRIFT-UNKNOWN`으로 실패한다. origin이 불통이면 릴리스 비교는
  `BEHIND-UNKNOWN` 경고로 degrade한다.
- **중복 억제**: 같은 tick에서 미러 체크가 이미 `release-stale`를 FAIL로 소유하면 독립
  프로브는 WARN으로 낮아져 사고당 수리 티켓이 하나만 생긴다. 독립 프로브의 enforcement는
  기본 0(WARN)이며 승격은 OWNER 결정이다.

## 릴리스 전환 유예

릴리스 포인터가 먼저 바뀌고 영수증·스킬 마운트·워처 래퍼가 따라오는 동안에는 세 체크가
`RELEASE-SWITCH-GRACE-WARN`으로 최대 15분만 유예된다. 정상 반영이 10분 이내에 끝나는
점을 고려한 여유이며, 15분부터는 기존 FAIL로 돌아온다. 포인터 심링크와 릴리스 디렉터리의
mtime이 모두 15분 미만이어야 하므로 같은 세대 재활성화로 유예가 늘어나지 않는다.
보존 디렉터리의 설치 순서와 `.origin-sha`로 직전 세대를 확인하며, 그 세대의 유효한
영수증 또는 아직 없는 영수증, 직전 내용 그대로인 스킬만 유예한다. 시각·순서·파일을
읽지 못하거나 무관한 영수증·마운트, 누락·고아 스킬이면 즉시 FAIL이다. 로컬 읽기뿐이므로
SSH 허용 명령은 추가하지 않는다.

워처 래퍼(`watcher wrappers match the release`)는 두 경우만 유예한다(2026-10-17).
계정 홈 사본이 **직전 릴리스 바이트 그대로**이거나, **이번 릴리스에 새로 생긴 행**이라
아직 복사되지 않았거나 SSH 허용 목록이 갱신되기 전이라 읽히지 않을 때다. 이 경우 로그에
`WATCHER-DRIFT-GRACE:` 줄과 `WATCHER-DRIFT-GRACE-PASS`가 남는다. 직전 릴리스와도 다른
바이트, 직전에 있던 행의 부재·판독 불가, 15분이 지난 전환은 예전처럼 FAIL이다. 계기는
두 번의 단발 오탐이다. 10-16 v1.39.0 때는 래퍼 복사 전 스윕이 `differs`로, 10-17 v1.46.0
때는 새 래퍼 `effect_request_watch.py` 읽기가 허용 목록 갱신(09:00:32 UTC) 3초 전에
`not allowlisted`로 실패해 소유자 알림과 수리 티켓이 났고, 둘 다 다음 스윕에서 PASS였다.

- **예**: 릴리스 직후 스윕에서 새 워처 읽기가 아직 거부됨 → `WATCHER-DRIFT-GRACE: agent:.hermes/scripts/<새 래퍼> is new in this release and not readable yet`, 체크 PASS(경고), 알림 없음.
- **거부**: 전환 20분 뒤에도 같은 상태 → `WATCHER-DRIFT-UNKNOWN`, 체크 FAIL, 알림과 수리 티켓.
