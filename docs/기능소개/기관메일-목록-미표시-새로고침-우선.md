# 기관메일 목록이 안 그려지면 먼저 새로고침해 본다 — 어느 길로 찾았는지 남긴다

## 무엇을

기관메일 동기화·발송은 로그인 뒤 메일 목록에서 받은메일함 번호를 읽는다. 90초를 기다려도 목록이
그려지지 않으면, 이제 메뉴 옆 번호(서버 확인 뒤 사용)로 넘어가기 **전에** 페이지를 최대 2번
새로고침하고 매번 30초까지 목록을 기다린다. 새로고침 뒤 목록이 나오면 그 목록에서 번호를 읽는다.
발송은 어느 길로 번호를 찾았는지(`rows` 첫 로딩, `reload-1`·`reload-2` 새로고침, `sidebar` 메뉴)를
`send-attempts.jsonl` 의 `list_path` 에 남긴다.

## 왜

2026-10-12 승인된 메일 두 통이 목록이 안 그려져 보내기 전에 멈췄고(v1.22.1 에서 메뉴 번호 대체로
해결), 소유자가 "이때 새로고침하면 안 그려져?" 라고 물었다. 실측(읽기 전용 로그인 20회, 발송 없음):

- 첫 로딩 목록 정상 19회(3.2~7.5초), 미표시 1회(8초 시점 행 0, 화면 주소에 앱 해시 없음 —
  운영 실패와 같은 모양).
- 새로고침은 실제로 문서를 다시 띄우고(로딩 시각이 바뀜) 로그인 세션을 유지했으며, 목록이
  15/15 다시 그려졌다(1.1~10.7초).
- 노드 로그 838회 로그인 중 목록 미표시 5회는 **전부 로그인 페이지 열기가 시간 초과된 로그인**
  (2026-10-06 03:52~05:12 UTC, 2026-10-12 03:24~07:22 UTC 두 구간)에서만 났다. 같은 구간에서 4분
  뒤 새 세션으로 다시 로그인해도 실패했다.

그래서 새로고침은 **원인 제거가 아니라 완화**다. 원인은 웹메일 쪽 지연 구간으로 보이고, 그
구간에서 새로고침이 얼마나 듣는지는 아직 관측되지 않았다 — `list_path` 기록이 다음 지연 구간에서
그 답을 준다.

## 사용 시나리오

- **새로고침으로 풀리는 날**: 소유자가 메일 카드에 ✅ → 로그인, 목록 0행 90초 → 새로고침 → 목록이
  그려짐 → 그 목록의 번호로 중복 확인·발송·보낸메일함 확인. 로그에 `mail list rendered after reload
  1/2`, 발송 기록에 `"list_path":"reload-1"`.
- **새로고침도 안 듣는 날**: 2번 새로고침해도 0행 → 예전처럼 메뉴 번호를 서버에 확인받아 계속
  (`"list_path":"sidebar"`). 그것도 안 되면 발송 전에 멈추고 `cause: mailbox_list_unavailable`.
  추가로 걸리는 시간은 최대 약 1분이다.
- 동기화(받은메일함 수집)도 같은 순서를 쓰고 로그에 `inbox folderUid … resolved by reload-1` 처럼
  남긴다.
