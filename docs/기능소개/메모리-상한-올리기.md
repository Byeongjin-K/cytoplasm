# 메모리 상한 올리기 — USER.md 3,000자 · MEMORY.md 3,300자

## 무엇을

에이전트(agent·peer)가 매 세션 시스템 프롬프트에 싣는 Hermes 자체 메모리의 상한을 올렸다:
USER.md 1,375 → **3,000자**, MEMORY.md 2,200 → **3,300자**. 값은 저장소 한 곳
(`automation/hermes_memory_config.py` 의 `LIMITS`)에만 있고, 릴리스가 두 계정의
`~/.hermes/config.yaml` 에 그 값을 쓰고 게이트웨이를 함께 재시동한다. 메모리 큐레이터의 상한(`CAPS`)도
같은 값을 읽는다.

## 왜

USER.md 가 Hermes 기본 상한 1,375자 중 1,355자(98.5%)를 쓰고 있어 새 사실 하나 넣을 자리가 없었다
(2026-10-14 조사). 상한은 Hermes 기본값일 뿐이고 설정 키 `memory.user_char_limit`·`memory.memory_char_limit`
로 바뀐다. 그런데 저장소는 그 값을 관리하지 않아 바꾸려면 노드에서 손으로 고쳐야 했고, 큐레이터는
옛 값(2,200·1,375)을 하드코딩하고 있어 상한만 올리면 계속 "거의 꽉 참" 을 보고했을 것이다.

소유자 결정(Q138, 2026-10-14): 「①②③ 다 (추천: ① 오늘, ②·③은 이어서)」 — 이 문서는 ①이다.
②(사람 정보를 USER.md 밖으로)와 ③(매 턴 자동 회상)은 이어지는 릴리스가 맡는다.

## 사용 시나리오

- **릴리스(정상)**: 릴리스 카드 ✅ → `deploy_all.sh --apply` 가 노드에서 두 계정의 설정을 관측한다
  (`v2:config;algorithm=hermes-memory-limits-v1`). 값이 다르면 `automation/memory_curator/deploy.sh` 가
  공용 헬퍼 `converge_config` 로 각 계정 안에서 릴리스 트리의 모듈을 돌려 두 키만 고치고(백업
  `config.yaml.bak-memory-limits-<UTC>` → 원자적 교체), 다시 읽어 확인한다. 선언이 `activation=gateway`
  라 agent+peer 게이트웨이를 함께 재시동하고, 다음 세션부터 큰 상한이 적용된다.
- **이미 맞음**: 다음 릴리스부터는 관측이 `ok` 라 아무것도 쓰지 않고 재시동도 하지 않는다.
- **memory 블록이 없는 계정**(peer 처럼 Hermes 기본값을 쓰던 계정): 두 키만 든 `memory:` 블록을 끝에
  붙인다. Hermes 는 설정을 기본값 위에 병합하므로 다른 메모리 설정은 기본값 그대로다.
- **해석할 수 없는 설정**(같은 키 두 번, 한 줄 매핑, 숫자가 아닌 값): 관측은 `unknown`, 배포기는 쓰지
  않는다 — 영수증이 막히고 사람에게 넘어간다.
- **상한을 다시 내릴 때**: `LIMITS` 를 낮추면 그 파일이 이미 새 상한보다 긴 계정에서는 거부한다(rc 7,
  `HERMES-MEMORY-LIMITS-REFUSED`). 업스트림 결함 NousResearch/hermes-agent#133028(열림) 때문이다 —
  파일이 상한보다 크면 정리·삭제 쓰기까지 거부돼 메모리가 갇힌다. 파일을 먼저 줄이고 내린다.
- **확인**: 노드에서 `cd /srv/autophagy-agent-current && sudo -n -u agent -H python3 -m automation.hermes_memory_config --check`
  (peer 도 같다) → `HERMES-MEMORY-LIMITS ok have=memory_char_limit=3300,user_char_limit=3000`.

## 비용

매 턴 프롬프트가 최대 약 2,700자 늘어난다((3,000−1,375)+(3,300−2,200)). 스냅샷은 세션 시작 때 고정되므로
세션 안에서 프롬프트 캐시는 깨지지 않는다.
