# 소비 노드의 첫 전량 반영이 막히지 않는다

## 무엇을
릴리스를 받아 쓰기만 하던 노드가 처음 전량 반영(`deploy_all.sh --apply`)을 할 때 막히던 다섯 곳을 고쳤다. 남은 하나는 절차로 안내한다. 순서는 새 [소비 노드 갱신 가이드](../guide/소비-노드-갱신.md)에 있다.

## 왜
2026-10-19 외부 노드 운영자가 v2.4.0을 정상 경로로 처음 전량 반영하다 여덟 곳에서 막혔고, 그 기록을 PR #104로 보내 줬다. 몇 곳은 조용히 해로웠다. 예를 들어 영수증이 없는 노드에서는 새 릴리스마다 소유자가 멈춘 게이트웨이가 다시 켜졌다.

## 바뀐 것
- **게이트웨이 정지가 유지된다**(8번): 승인된 정지가 배포 영수증 옆에 ops 표식을 남긴다. 영수증이 없는 노드의 리컨실러는 그 표식으로 정지를 알아본다.
- **옛 노드의 interop 배포**(3번): 게이트 코드가 아직 없는 옛 런타임은 릴리스 트리로 새 규칙을 확인한다. 게이트가 있는 런타임은 예전처럼 그 코드로 확인한다.
- **memory-choices 폴더**(2번): ops 가 서비스 그룹 밖이어도 setgid 를 상속으로 받는다. setgid 만 빠진 빈 폴더는 다시 만들고, 누가 풀어 놓은 폴더는 여전히 거부한다.
- **설치한 적 없는 옛 서비스**(7번): 끄기 스위치가 그 유닛을 이미 꺼진 것으로 보고 끝난다. 실제 실패는 어느 유닛인지 한 줄 남긴다.
- **새 Hermes 경고 문구**(1번, PR #104 원작성자 커밋): 게이트웨이를 멈춘 노드에서도 cron 목록을 읽는다.
- 4번(서명 태그 기준 배포)은 `DEPLOY_PROVENANCE_REF` 로 안내한다. 5번(끈 작업을 다시 켬)은 다음 릴리스에서 고친다.

## 사용 시나리오
- 소비 노드 운영자가 새 태그로 체크아웃한다. `DEPLOY_PROVENANCE_REF=<태그>` 로 `--rehearse` → `--plan` → `--apply` 를 돌리면 영수증이 생긴다. 다음 릴리스에서도 멈춘 게이트웨이는 그대로 멈춰 있다.
- 공유 폴더가 0777 로 풀려 있으면 여전히 거부된다. 그 폴더는 사람이 원인을 보고 고친다.
