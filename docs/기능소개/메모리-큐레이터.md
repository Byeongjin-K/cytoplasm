# 메모리 큐레이터 (memory curator)

> 2026-10-19 소유자 “끄지 말고 삭제” 결정으로 agent 메모리 예약 작업을 삭제했다. 아래 자동 처리 설명은 과거 기록이며 현재 예약되지 않는다. 원본·상태·백업·공유 CLI·피어 재생은 보존한다. [삭제 범위](끈-정기-작업-삭제.md).

## 무엇을

Hermes **자체 메모리**(`~/.hermes/memories/MEMORY.md`·`USER.md`)를 주기적으로 정리·관리하는 no-agent 큐레이터. 네 가지를 한다:

1. **무손실 정리(자율)** — `§`로 구분된 항목에서 완전 중복만 제거하고 공백을 다듬는다. 정보를 버리지 않으므로 소유자 승인 없이 적용한다(백업 후 원자적 쓰기, 되돌리기 가능).
2. **트윈 승격 제안(오너-DM ✅)** — 원칙·결정·선호 같은 **지속적 판단**을 감지해 의사결정 트윈 초안으로 올린다. `prepared`→`posted` 상태를 남겨 실패·크래시 뒤에도 같은 항목을 재시도하고, 틱당 최대 3건은 자체 메모리에서 가장 많은 글자를 확보하는 후보부터 제안한다(동률은 kind·digest로 고정). 큐레이터는 제안자이므로 `provenance:observed`·`authority:advisory` 상한(SI-3)을 지킨다.
3. **검증 후 자체 메모리 삭제** — cha의 ✅로 트윈 노트가 실제 저장된 뒤, 승인된 노트 바이트 해시·삭제 마커·원본 항목의 source-qualified digest가 모두 일치할 때만 그 항목 하나를 백업 후 삭제한다. 누락·변조·중복·파일 드리프트는 전부 fail-closed로 보류한다.
4. **독립 owner notice + 변화 감지 경보** — 승격 확인 메시지 게시·검증 후 삭제 완료는 v3 상태의 durable outbox에 `promotion_key#phase`로 먼저 기록하고, near-cap cooldown이 `hold`/`silent`여도 별도 설명 DM으로 한 번 보고한다. 전송 실패 시 outbox를 유지해 다음 틱에 at-least-once 재시도한다. 반복 가능한 `⚠️ near-cap` 줄만 캡 구간·승격/검증 상태·수동 확인 사유의 서명 변화와 24시간 cooldown을 따르며, 성공 전에는 `last_sent`를 전진시키지 않는다.

## 왜

Hermes 자체 메모리는 의도적으로 작다(기본 MEMORY.md 2,200자 / USER.md 1,375자 — 2026-10-14 부터 이 저장소는 3,300자 / 3,000자로 올려 쓴다, [메모리 상한 올리기](메모리-상한-올리기.md)). 가득 차면 **자동 정리가 없고**, 한도를 넘는 새 정보는 **조용히 거부**되며, "정리해줘"조차 실패하면서 "정리했습니다"라고 잘못 보고한다. 실제로 두 파일이 99.5%·97.5%까지 차 있어, cha가 선언한 원칙이 저장되지 못하고 사라졌다. 큐레이터는 durable 판단을 트윈(무제한·자동정리·출처추적·recall)으로 옮겨 캡 여유를 확보하고, 짧은 사실만 자체 메모리에 남긴다. 과거 대화 회상은 이미 `session_search`(state.db FTS5+한국어 trigram)가 맡으므로 자체 메모리가 대화 이력을 떠안을 필요가 없다.

## 사용 시나리오

- **happy**: cron 틱 → 중복 제거 → durable 후보 ≤3건을 **오너-DM 확인 메시지**로 게시 → cha가 ✅ → 위키 게이트가 트윈 노트로 저장 → 다음 틱이 해시·마커·원본 digest를 검증 → 해당 자체 메모리 항목만 백업 후 삭제 → cooldown 상태와 무관하게 삭제 건수·확보 글자 수를 한 번 알림. **확인 메시지 자체가** 트윈 종류·**원문 전체**(토큰 모양 문자열은 마스킹, ─── 펜스 안)·"✅ 시 자체 메모리에서 삭제, 이후 recall로만" 문구를 실어 소유자가 무엇을 인가하는지 한 메시지에서 알 수 있다(요약은 owner-dm 표면에서만 붙는다 — 아래 「안전」). 같은 틱의 별도 요약 DM은 여러 건을 한번에 조망하는 용도로 그대로 남는다.
- **거부/대기**: cha가 ⛔하거나 아직 반응하지 않으면 원본은 그대로다. 게시 실패는 `prepared`로 남아 다음 틱에 재시도하고, 노트 누락은 정상 대기로 취급한다. 노트 해시·마커 불일치나 동일 원본 중복은 수동 확인 사유로 남기며 삭제하지 않는다.
- **안전**: 삭제는 `decide_reconcile == delete` 뒤 `delete_entry` 한 경로에서만 일어난다. 승인은 위키 스킬의 검증된 `create_draft`+`post_confirm_message` 경로를 그대로 재사용하며, 큐레이터는 `approval_lifecycle`를 재구현하지 않는다. 확인 메시지의 요약은 호출자가 명시적으로 넘겼고 **해석된 표면이 `owner-dm`일 때만** 붙는다 — 위키 본문은 특허 민감일 수 있어 그 표면 밖으로 나가면 안 되기 때문이고, 표면을 확인할 수 없으면 요약을 생략한다(fail-closed). 저장된 원칙은 판단 근거일 뿐 실행 권한이 아니다(SI-1).
- **운영 조회**: `python3 -m automation.memory_curator`는 기존 dry-run 정리 보고, `reconcile --dry-run`은 외부효과 없이 한 사이클의 예정 작업을 계산, `state show`는 영수증 ID·해시·비공개 경로를 가린 상태를 출력한다.
- **레거시 회수(소유자 실행)**: v1에서 승격됐던 `legacy_unbound` 항목은 옛 승인(마커 없음)이라 자동 삭제되지 않는다. `legacy_rebind`가 그 레코드를 열어 다음 틱이 **삭제를 명시한 새 마커 확인 메시지**로 재승격하게 한다(아무것도 삭제하지 않음). 노드에서는 릴리스 런타임에서 `cd /srv/autophagy-agent-current && python3 -m automation.memory_curator.legacy_rebind --max 3`로 실행한다(워처도 같은 릴리스 트리를 import 하므로 같은 상태 파일을 갱신한다. 예전 홈 사본 `~/.hermes/memory_curator_runtime` 은 retired 로 선언된 옛 세대라 쓰지 않는다. 개발 체크아웃에서는 `python3 -m automation.memory_curator.legacy_rebind`). 재개는 틱당 최대 3건씩 재제안되므로 4건 이상이면 틱을 여러 번 돌려야 한다. cha가 확인 메시지에 ✅하면 다음 틱이 검증 후 해당 항목을 삭제한다. 실측 증적: `docs/qa/MC-4/legacy-rebind.txt`.
- **분류 shadow(비파괴 진단)**: 자체 메모리의 80%는 인프라/운영 사실이라 durable cue 매칭에 안 걸려 정리 대상이 아니다. LLM 분류기(glm-main, 주입형)가 각 항목을 `TWIN`(규범 판단)·`OPS_REFERENCE`(경로/포트/절차 등 recall 가능한 운영 사실)·`KEEP_NATIVE`(신원·전역 스타일·안전/승인·recall前 라우팅 — 결정적 veto)·`UNCERTAIN`으로 라우팅한다. 민감(특허)·credential 형태·keep-native cue는 **LLM에 보내기 전** 결정적으로 닫는다. `cd /srv/autophagy-agent-current && python3 -m automation.memory_curator.shadow_cli --kind both --offline`(LLM 없이 veto 히스토그램만) 또는 `--full`(glm 라이브, 원문 노출)로 **쓰기·게시·삭제 0**의 진단 리포트(`memory-curator-shadow-v1`)를 출력한다. 핵심 지표 `cue_recall.classifier_only`=15개 리터럴 cue가 놓친 진짜 durable 규칙 수. cron은 여전히 LLM-free(분류기 미주입, `test_memory_curator_cron_is_llm_free`가 강제) — 분류는 소유자 수동 실행뿐이다. 운영 사실의 실제 재배치·삭제(공간 회수)는 shadow 검토 후 별도 오너 게이트 라운드(MC-4)로 진행한다.

## 대기 리마인더와 통지 봉투

- 대기 확인은 `Ref`로 보관하고 공유 `discord_link`로만 링크를 만든다. 저장된 `surface`가
  `owner-dm`/`dm`이면 `space="dm"`으로 `@me` 링크를 유지한다. 길드 초안은 저장된
  `approval_guild_id`를 쓰며, 길드 좌표나 공간이 없으면 초안 id로 Discord 검색을 안내한다.
  게시된 초안에 채널·메시지 좌표가 없거나 비어 있어도 알림을 생략하지 않고,
  URL 없는 `Ref(scope="resource")`에 중립 검색 라벨과 초안 id만 담는다. 제목·위키 본문은
  싣지 않으며 요약의 기존 마스킹을 유지한다. 형식이 잘못된 좌표와 사라진 초안은 제외한다.
  링크를 확인하려고 네트워크를 조회하지 않는다.
- **0~9시 KST에는 보내지 않으며, 3시간 간격과 빈 알림 금지는 그대로다.** 전송 성공 때만
  리마인더 표식을 전진시킨다. 승인 카드의 게시·삭제·리액션은 건드리지 않는다.
- `alert_owner`는 지원되는 런타임에서 소유자 통지 파사드에 5필드 봉투를 넘긴다. 기존 문자열
  콜백이 가진 점검 결과와 리마인더 목록은 사실 필드에 담되, 채널·메시지 좌표가 없는
  초안의 검색 안내는 중복 없이 위치 필드의 `Ref(scope="resource")`로 전달한다.
  그 외 점검의 위치는 기존대로 해당 없음이다. `Result`의 완료는 **점검 완료**이지
  승인·삭제 완료가 아니다. 가상 `Periodic` 기간을 만들지 않는다.
  봉투 import가 불가능하거나 파사드에 지원 플래그가 없으면 기존 문자열을 바이트 그대로 보낸다.
  통지 목적지·실패 반환값·outbox 재시도 정책은 바꾸지 않는다.

## 관련

- 코드: `automation/memory_curator/`(watch·watch_steps·reporting·state·binding·reconcile·deletion·alerting·effects·cli) + `cron/memory_curator_watch.py`(no-agent flock 워처)
- 재사용: 위키 게이트(`skills/wiki/scripts/wiki_gate.py`의 `create_draft`·`post_confirm_message`), `automation/interop/approval_lifecycle.py`(보안 경계, 무접촉)
- 관련 규약: 의사결정 트윈 스키마(SI-1/SI-3/SI-6), AS-SSOT(오너-DM 승인 표면), no-agent 워처-cron 설계규약
- 배포: 워처 래퍼만 → `~/.hermes/scripts/`(`automation/memory_curator/deploy.sh`), cron 은 `converge_cron` 으로 `every 30m` no-agent 등록을 수렴. 패키지는 래퍼가 시작할 때 고르는 릴리스 트리(`/srv/autophagy-agent-current`)에서 import 하므로 릴리스마다 저절로 따라온다 — 옛 홈 사본 `~/.hermes/memory_curator_runtime/` 은 `v2:tree;policy=retired` 로 선언돼 남아 있을 뿐 실행되지 않는다(지우지 않음). 위키 게이트 런타임 env 필요(DISCORD_BOT_TOKEN·INTEROP_CONFIG·AUTOPHAGY_REPO_ROOT·WIKI_ROOT·WIKI_GATE_DIR). 활성화·첫 라이브 승격은 소유자 ✅ 라운드.
