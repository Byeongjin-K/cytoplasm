# 기관메일을 평일 근무시간 매시 수집한다 — 수집이 멈추면 소유자에게 한 번 알린다

## 무엇을

- 새 cron `mail-sync-watch` 가 평일(월~금) 09:20~19:20 KST 매시 20분에 기관메일을 수집한다. (2026-10-19부터 매일 07:00~24:00 10분마다 — [기관메일 10분 수집·지금 수집](기관메일-10분-수집과-지금-수집.md))
  수집은 다이제스트가 쓰던 기존 경로(`mail_wrapper.py list --sync`) 그대로다. 실패한 시각은 다음 시각에
  다시 시도되고, 놓친 메일은 평소 증분 수집이 이어서 저장한다(한 번에 최대 50건).
- 수집이 **3회 연속**(약 3시간) 실패하면 소유자에게 한 번 알리고, 회복되면 한 번 더 알린다.
  로컬 DB 폴백(동기화 구조 실패)도 실패로 센다 — 그때는 아무것도 새로 저장되지 않기 때문이다.
- 수집은 성공하는데 새로 저장된 메일이 **6회 연속** 0건이면 따로 한 번 알린다. 평일 근무시간에
  여섯 시간 동안 메일이 하나도 없다면 대개 웹메일 목록이 비어 보였다는 뜻이다.
- 제한 시간(900초)에 걸린 동기화는 먼저 SIGTERM 을 받아 run 을 `fail` 로 남기고 브라우저를 닫는다.
  30초 안에 끝나지 않을 때만 강제 종료한다. 끝나지 못한 run(2시간 넘게 `running`)은 다음 동기화가
  `abandoned` 로 닫는다.
- 08:00 다이제스트 워처가 `GATE-REFUSED DIGEST-FAIL …` 처럼 접두어가 붙은 실패 마커도 읽는다.

## 왜

2026-10-13, 노드에 저장된 기관메일이 15:36 KST 이후 멈췄다. 읽기 전용 진단 결과(배포 회귀 아님):

- 정해진 수집은 08:00 다이제스트 안의 동기화 **하나뿐**이었다. 그날 08:00 은 공유기 DNS 장애로
  `ERR_NAME_NOT_RESOLVED` 실패했고(09-24~09-28 08:00 에도 같은 실패가 다섯 번 있었다) 재시도가 없었다.
- 다이제스트 실패 통지도 같은 DNS 장애로 전달되지 못했다. 워처는 자식이 낸 마커 앞의 `GATE-REFUSED`
  접두어 때문에 마커를 못 읽고 `stage=runner code=child_exit` 로 바꿔 적었다.
- 15:29 에 수동으로 띄운 동기화 둘은 느린 웹메일(목록 미표시·CDP 시간 초과)에서 900초 제한에 걸려
  강제 종료됐다. run 은 `running` 으로 남았고 브라우저는 15시간 동안 살아 있었다.
- 그래서 다음 날 08:00 까지 새 메일이 저장되지 않았고, 저장된 메일을 읽는 프로젝트 보드 자동 분석도
  새 메일을 보지 못했다. 소유자는 아무 안내도 받지 못했다.

## 사용 시나리오

- **평소**: 평일 10:20 틱 → 동기화 성공, 새 메일 3건 저장 → 아무 말 없음. 프로젝트 보드의 다음 분석
  틱이 그 메일을 읽는다.
- **장애**: 11:20·12:20·13:20 세 번 연속 DNS 실패 → 13:20 에 한 줄
  `mail-sync-watch failed 3 ticks in a row: 기관메일 수집 실패(매시 동기화) — rc=2 error_code=… failure_signature=…`.
  14:20 에 회복되면 `mail-sync-watch recovered after 3 consecutive failures (…UTC) — last failure: …`.
  놓친 메일은 14:20 동기화가 저장한다.
- **목록이 비어 보임**: 수집은 성공인데 새 메일 0건이 6회 이어지면 `mail-sync-quiet failed 6 ticks in a row: …`
  한 줄. 소유자는 웹메일에 실제로 새 메일이 있는지 본다.
- 임계값은 노드 `~/.env.secrets` 의 `MAIL_SYNC_ALERT_AFTER`·`MAIL_SYNC_QUIET_AFTER`(틱 수)로 바꾼다.
  공휴일은 따로 빼지 않는다 — 그날도 매시 수집할 뿐이다.
