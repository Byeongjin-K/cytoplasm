# 기관메일 발송이 메일 목록이 안 보여도 멈추지 않고, 실패하면 원인을 남긴다

## 무엇을

승인된 기관메일 발송은 보내기 전에 받은메일함 번호를 찾아 중복 발송 여부를 확인한다. 웹메일이
로그인 뒤 메일 목록을 화면에 그리지 않으면, 이제 동기화와 같은 방법(메뉴 옆 받은메일함 번호를
서버에 확인받은 뒤 사용)으로 계속 진행한다. 그리고 발송이 실패하면 초안 기록에 **어느 확인에서
멈췄는지**를 고정된 원인 코드(`cause`)로 남긴다.

## 왜

2026-10-12 소유자가 ✅ 한 메일이 두 번 연속 `send_failed` 로 멈췄고, 그 뒤 mail-mode 가 no-go 로
내려갔다. 로그인은 성공했지만 웹메일이 메일 목록을 그리지 않아 발송 전 확인 단계가 받은메일함
번호를 찾지 못한 것이 원인이었다(메일은 나가지 않았다). 같은 상황을 동기화는 2026-10-06 에 넣은
대체 경로로 이미 넘기고 있었는데, 발송 경로에는 그 대체가 없었다. 게다가 초안 기록에는
`error_code=send_failed` 만 남아 인증 문제인지 웹메일 문제인지 알 수 없었다.

## 사용 시나리오

- **목록이 안 그려지는 날**: 소유자가 메일 카드에 ✅ → 로그인 성공, 목록 0행 → (2026-10-12 부터 먼저
  페이지를 최대 2번 새로고침해 본다 — [새로고침 우선](기관메일-목록-미표시-새로고침-우선.md)) → 메뉴의
  받은메일함 번호를 찾아 목록 API 가 같은 폴더라고 답하면 그 번호로 중복 확인 → 발송 → 보낸메일함에서
  확인. 로그에 `current folder uid … resolved by sidebar` 한 줄이 남는다.
- **대체도 실패하는 날**: 메뉴 번호를 서버가 확인해 주지 않으면 예전처럼 발송 전에 멈춘다(fail-closed).
  초안 `last_error` 에 `cause: mailbox_list_unavailable` 이 남고, 실패 문구에도 `cause=` 가 붙어
  에이전트가 "로그인은 됐지만 웹메일 목록을 읽지 못해 보내기 전에 멈췄다"고 정확히 말한다.
- **원인 코드**: `login_failed`, `browser_command_failed`, `mailbox_list_unavailable`,
  `compose_csrf_missing`, `compose_form_incomplete`, `send_trigger_missing`,
  `send_post_http_error`, `send_post_missing`, `sent_mail_unconfirmed`, `send_lock_busy`,
  첨부 단계의 `attachment_*` 들. 오류 원문은 여전히 기록에 싣지 않는다 — 원인 코드만 싣는다.
