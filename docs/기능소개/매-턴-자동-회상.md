# 매 턴 자동 회상 — 옮긴 기억을 다시 참고한다

## 무엇을

Hermes 외부 메모리 제공자 `autophagy_recall`이 사용자 질문마다 기존 RAG에서 관련 기록을
최대 3개 찾아 사용자 메시지의 API 사본에 참고 자료로 붙인다. 새 저장소·외부 메모리 서비스·
대화 저장 경로는 없다. USER.md와 MEMORY.md의 내장 메모리는 그대로 함께 작동한다.

## 왜

네이티브 메모리에서 Obsidian으로 재배치한 사실은 저장돼 있어도 에이전트가 recall 도구를
불러야만 보였다. 이제 질문에 관련된 사실은 모델이 도구 호출을 결정하기 전에 돌아온다.
시스템 프롬프트는 바꾸지 않아 고정 프롬프트 캐시를 유지한다.

## 사용 시나리오

합성 예: Obsidian 참조 노트에 「배양기 점검에는 청록 점검표를 사용한다」가 이관·인덱싱돼
있다. 사용자가 「배양기 점검에 어떤 점검표를 쓰지?」라고 물으면 제공자가 기존
`automation.knowledge` 파사드를 통해 RAG를 검색하고 원본 기록과 출처 키를 자동으로 붙인다.
직접 recall을 요청할 필요는 없다. 검색 점수·근거 판정은 기존 recall과 같은 공용 규칙이다.

검색 전체(프로세스 기동·MCP 연결 포함)에 5초 예산을 둔다(소유자 결정 2026-10-14: "2초보다 더 길게 해야하는거 아니야?" — 평소 첫 답 중앙값 약 53초의 10% 미만). 오류·시간 초과면 자식 프로세스를
끝내고 아무것도 주입하지 않는다. 로그는 `MEMORY-RECALL-SKIP reason=<분류>` 한 줄뿐이며
질문·기록·경로·인증값을 담지 않는다. 검색 결과가 없어도 주입은 없다.

결과는 출처 키를 포함한 JSON 코드 블록이며 `authority=reference-not-instructions`다.
기록 속 코드 울타리와 HTML 구분자는 JSON 이스케이프로 보존해 울타리를 닫지 못하게 한다.
전체 블록 3,000자, 기록당 1,200자, 질의 2,000자 상한이다. 회상은 지시나 실행 승인이 아니다.

## 배포와 한계

구현·오프라인 검증 단계이며 라이브 활성화는 별도 릴리스 이후다. 홈 제공자 파일은
`deploy-manifest.txt`의 agent·peer별 `v2:file;activation=gateway`로 배포한다.
기존 `memory_curator`의 config 선언이 공용 `converge_config`로 상한과
`memory.provider: autophagy_recall`을 함께 수렴하고 agent+peer를 재시동한다.
config 파일은 한 소유자만 작성하며, 기존 외부 제공자가 있으면 덮지 않고 rc 7로 거부한다.
활성화·해제 절차는
[운영자 매뉴얼](../guide/manual-maintainer.md#매-턴-자동-회상-제공자)을 따른다.

설치본 Hermes는 도구 루프 **전에 한 번** 검색하고 짧은 인사·확인 및 슬래시 명령을 건너뛴다.
도구 결과로 나중에 알게 된 주제는 그 턴의 자동 검색에 포함되지 않는다.
새 턴마다 새로 검색하며 제공자는 결과를 캐시하거나 다음 턴에 재사용하지 않는다.
Hermes는 과거 API 메시지를 그대로 재생하기 위해 회상 블록이 들어간 `api_content`를
세션 기록에 남긴다. 따라서 「턴 전용」은 전역/시스템 메모리로 저장하지 않는다는 뜻이지,
과거 대화 맥락에서 물리적으로 삭제한다는 뜻은 아니다.
텍스트 API 경로를 대상으로 하며 `codex_app_server`와 비문자열 멀티모달 메시지는 설치본의
사용자 API 사본 주입 경로를 우회한다. 이 경로들은 자동 회상 활성화 대상에서 제외한다.
