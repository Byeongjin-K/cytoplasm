# 매 턴 자동 회상 — 옮긴 기억을 다시 참고한다

## 무엇을

Hermes 외부 메모리 제공자 `autophagy_recall`이 사용자 질문마다 **저장소 전체**를 검색해
노트당 한 문단씩 상위 100개 후보를 받고, 계정 주 모델이 한 번 읽어 그 일에 필요한 사실이
적힌 문단을 최대 4개 골라 사용자 메시지의 API 사본에 참고 자료로 붙인다. 에이전트가
`recall` 스킬을 직접 부를 때도 같은 고르기를 쓴다. 새 저장소·새 검색 서버·새 색인은 없고,
범위 필터로 저장소를 좁히지도 않는다. USER.md·MEMORY.md 내장 메모리는 그대로 함께 작동한다.

## 왜

형 질문(2026-10-15 Q150): "Recall 기능을 고쳐야 하는거 아니야?" · 06:19: "전체 저장소에서
필요한걸 잘 찾는게 목적이야. 그리고 이미 임베딩이 되어있는데 왜 잘 못찾는지도 궁금해".
질문 붙이기(doc2query)는 Q155에서 접었다("대단히 부작이 스러워").

옮긴 기억 23개에 대한 형 말투 질문(세트 A)으로 재 보니, 필요한 사실이 든 문단은 기존 검색
상위 50 안에 35/46 있었지만 상위 3 안에는 13/46뿐이었다. 형 말투가 그 노트보다 긴 대화
기록·비슷한 노트에 더 가깝게 잡히고, 점수 문턱은 맞는 것과 엉뚱한 것을 가르지 못했다
(코사인 0.55에서 정답 21 대 엉뚱한 것만 21). 저장은 되어 있고 **순서**가 문제였다. 노트당 한
문단으로 접어 100개를 보여 주면 정답 노트가 39/46 질문에서 그 안에 있고, 모델이 그중
필요한 것을 고른다.

## 측정 (세트 A로 맞추고 봉인 세트 D로 한 번 판정)

| | 사실 붙음 (≥80%) | 엉뚱한 것만 (≤10%) | 무관 무첨부 (≥80%) | 지연 p95 (≤5 s) |
|---|---|---|---|---|
| 지금 검색 (세트 A) | 13/46 | 13/46 | 22/30 | 1.8 s |
| 고른 설정 (세트 A) | 38/46 | 3/46 | 30/30 | 고르기 4.8 s |
| 고른 설정 (세트 D, 한 번) | 39/46 (85%) | 5/46 (10.9%) | 30/30 | 고르기 5.0 s, 전체 6.9 s |

세트 D에서 엉뚱한 것만 붙은 비율은 기준을 한 질문 넘었고, 임베딩(CPU 약 1.7–2.2 s)을 포함한
전체 지연은 5초를 넘었다. 그래서 턴이 고르기를 기다리지 않게 했다(아래).

## 사용 시나리오

합성 예: Obsidian 참조 노트에 「배양기 점검에는 청록 점검표를 사용한다」가 이관·인덱싱돼
있다. 사용자가 「배양기 점검에 어떤 점검표를 쓰지?」라고 물으면 제공자가 기존
`automation.knowledge` 파사드로 저장소 전체를 찾아 노트당 한 문단씩 후보를 만들고, 모델이
그 노트를 골라 원본 기록과 출처 키를 붙인다.

고르기는 배경에서 돈다. 턴은 최대 5초(소유자 결정 2026-10-14: "2초보다 더 길게 해야하는거
아니야?")까지만 기다리고, 그 안에 끝나면 턴 시작에 붙는다. 늦으면 턴을 바로 시작하고, 끝나는
대로 Hermes `llm_request` 미들웨어가 **그 턴의 다음 모델 호출**(보통 첫 도구 결과 뒤)에
붙인다. 붙이는 위치는 처음 붙인 자리로 고정해 이후 호출의 프롬프트 앞부분을 바꾸지 않는다.
결과는 그 프리페치 뒤 첫 모델 호출의 턴(`turn_id`)에 묶여, 같은 말로 시작한 다음 턴에도 붙지 않는다. 검색 서버가 아직 예전 판이면(릴리스 중 재빌드 전이나 재빌드 실패 후 되돌림) 예전 검색 결과를 붙인다.

에이전트가 `recall_cli.py search`를 직접 부르면 같은 후보·같은 지시문으로 `codex_llm`(계정 주
모델)이 고른다. 모델이 답하지 못하거나 검색 서버가 아직 예전 판이면 예전 검색으로 돌아가고
응답의 `search.picked`가 `false`다. `RECALL_PICK=0`이면 고르기를 끈다.

오류·시간 초과면 아무것도 주입하지 않는다. 로그는 `MEMORY-RECALL-SKIP reason=<분류>`와
`MEMORY-RECALL-DEFER` 한 줄뿐이며 질문·기록·경로·인증값을 담지 않는다.

결과는 출처 키를 포함한 JSON 코드 블록이며 `authority=reference-not-instructions`다.
기록 속 코드 울타리와 HTML 구분자는 JSON 이스케이프로 보존해 울타리를 닫지 못하게 한다.
한 턴에 기록 최대 4건, 전체 블록 4,000자, 기록당 1,200자, 질의 2,000자 상한이다. 회상은 지시나 실행 승인이 아니다.

## 배포와 한계

구현·오프라인 검증 단계이며 라이브 활성화는 별도 릴리스 이후다. 홈 제공자 파일은
`deploy-manifest.txt`의 agent·peer별 `v2:file;activation=gateway`로 배포한다.
기존 `memory_curator`의 config 선언이 공용 `converge_config`로 상한과
`memory.provider: autophagy_recall`을 함께 수렴하고 agent+peer를 재시동한다.
config 파일은 한 소유자만 작성하며, 기존 외부 제공자가 있으면 덮지 않고 rc 7로 거부한다.
활성화·해제 절차는
[운영자 매뉴얼](../guide/manual-maintainer.md#매-턴-자동-회상-제공자)을 따른다.

설치본 Hermes는 도구 루프 **전에 한 번** 검색을 시작하고 짧은 인사·확인 및 슬래시 명령을 건너뛴다.
도구 결과로 나중에 알게 된 주제는 그 턴의 자동 검색에 포함되지 않는다. 늦게 끝난 고르기는
도구를 한 번도 부르지 않고 바로 답하는 턴에는 붙지 않는다. 턴 중간에 붙인 블록은 Hermes가
세션 기록에 남기지 않는다(턴 시작 주입만 `api_content`로 남는다).
새 턴마다 새로 검색하며 제공자는 결과를 캐시하거나 다음 턴에 재사용하지 않는다.
Hermes는 과거 API 메시지를 그대로 재생하기 위해 회상 블록이 들어간 `api_content`를
세션 기록에 남긴다. 따라서 「턴 전용」은 전역/시스템 메모리로 저장하지 않는다는 뜻이지,
과거 대화 맥락에서 물리적으로 삭제한다는 뜻은 아니다.
텍스트 API 경로를 대상으로 하며 `codex_app_server`와 비문자열 멀티모달 메시지는 설치본의
사용자 API 사본 주입 경로를 우회한다. 이 경로들은 자동 회상 활성화 대상에서 제외한다.
