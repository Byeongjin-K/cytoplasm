# 노드 알림·승인 카드의 발신 봇을 유돌로

## 무엇을·왜

Hermes 게이트웨이를 멈춰도 정기 작업과 Ops 수리 워처는 별도 프로세스여서
예전 봇으로 계속 글을 보냈다. 릴리스 승인으로 이 발신 자격증명을 유돌로
통일한다. agent·peer·ops가 같은 해석기 `automation.notice_bot.resolve_token`을 쓴다.
토큰을 교체하는 것은 발신 신원뿐이며 소유자 반응·승인 해시·실행 게이트는 유지한다.
공용 전송기는 전송 직전에도 override를 확인하므로 전환 전에 시작한 승인 워처도 새 자격증명을 쓴다.

## 켜기·복구

릴리스 호스트의 `~/.hermes/release-flags/notice-bot`에 줄바꿈 없이 `yoodori`를 둔다.
`hermes-gateways-stopped`의 `stopped`와 `yoodori-channel`의 채널 선택도 함께 필요하다.
이 조합이 아니면 승인 계획·배포를 거부한다. 카드에는 다음 줄이 한 번 붙는다.

> 발신 봇 바꾸기: 노드 알림·승인 카드를 유돌 봇으로 보냄(Agent·Peer·Ops 봇은 아무것도 보내지 않음)

호스트의 기존 `~/.local/bin/yoodori-do`가 자기 계정의
`$HOME/.yoodori/dori.env`에서 `DORI_DISCORD_TOKEN`을 읽는다. 계정 홈을 코드에
고정하지 않는다. **토큰 SHA-256**만 `notice-bot:yoodori` 표면에 묶는다.
봇 ID만 묶으면 승인 뒤 같은 봇의 토큰 교체를 구별하지 못하므로 자격증명 바이트에 묶었다.
원문은 계획 JSON·카드·로그·argv에 넣지 않고 SSH stdin으로만 보낸다.
노드에서 실행하는 릴리스 승인 스테이징에는 `configs/node.example.toml`도 함께 실어
체크아웃 밖에서도 같은 override 경로를 해석한다.

소유자 승인 뒤 `deploy_all.sh`가 agent·peer의 `~/.hermes/notice-bot.json`,
ops의 노드 설정 `private_root/notice-bot.json`을 계정 소유 0600으로 원자 교체한다.
ops 경로는 수리 유닛의 `ProtectHome=yes` 밖이다. 기존 sudo 계정 전환만 사용하며
새 root 권한·노드 수작업은 없다. 영수증의 `notice_bot`에는 지문과 세 계정의
재조회 결과만 남고, 하나라도 다르면 전량 반영을 완료하지 않는다.

**예:** 메일 회신 초안을 요청하면 유돌 채널 아래 요청별 스레드에 유돌이 카드를
올린다. 공급망·릴리스의 새 승인 카드는 같은 채널 자체에, 타이머 출력과 정기 통지도
그 채널에 올라간다. 명시적 owner-DM 통지도 전환 중에는 그 채널을 사용한다.
과거 카드의 저장된 좌표·승인 결정을 바꾸거나 카드를 재게시하지 않는다.
과거 봇이 작성한 메시지의 수정·삭제 권한은 유돌 자격증명으로 생기지 않는다.

**거부·오류:** 승인에 없는 지문 또는 승인 이후 바뀐 토큰은 쓰기 전에 거부한다.
노드 override가 깨졌거나 읽을 수 없으면 값 없는 `NOTICE-BOT-WARN`을 내고
기존 토큰으로 돌아간다. 따라서 예전 토큰을 폐기하기 전 반드시 아래 검증을 한다.
스위치 삭제 후 재배포는 override만 제거하고 기존 비밀 파일은 그대로 복구 경로로 남긴다.
이미 폐기한 예전 토큰 자체를 되살리지는 않는다.

## 발신 경로와 원래 토큰 출처

| 경로 | 기존 출처 → 전환 |
|---|---|
| `owner_notice`(일반·DM·첨부), 지출·리마인더·연구동향, 자가 스킬 감사, 배포 리컨실·헬스체크 | agent/peer의 환경·`~/.env.secrets`, ops의 환경(`~/.env.secrets` 또는 `/etc/autophagy/repair-approval.env`) → 계정 override |
| 공용 Discord·reaction transport, approval directory, origin notice·digest thread의 주입 transport | 호출자가 전달한 토큰 → 공용 해석기(순수 lifecycle에는 I/O를 넣지 않음) |
| `repair_ops_discord`, repair report send/consumer | ops의 `/etc/autophagy/repair-approval.env`, agent의 환경 → 계정 override |
| `skill_gate`, supply-chain watcher·reminder, peer attest, release request/remote | agent/peer의 `~/.env.secrets` → 계정 override; 서명 peer 증명·소유자 승인 불변 |
| 메일·일정·예산·조율·할 일·위키·회의·구매 검토·특허 승인 | 환경 또는 `~/.env.secrets` → 계정 override |
| Plaud·메모리 이동·Obsidian·공용 외부효과·프로젝트 보드 | 워처가 로드한 환경 → 계정 override |
| `cron_timer_run deliver=discord` | 환경 → `~/.hermes/.env` → `~/.env.secrets` → override 우선; 목적지도 override 채널 |
| 관리형 스킬 제출·발행 통지 | 명시적 토큰 파일 또는 환경 → 노드 override(워크스테이션에 override가 없으면 기존 그대로) |
| 게이트 드라이버·인터롭 플러그인·소유자 대리 읽기/통지 | 환경 → 계정 override; 실제 Hermes 대화 발신은 게이트웨이 정지로 차단 |

적합성 시험은 직접 토큰 읽기를 금지하고 면제 사유를 원장으로 고정한다.
면제는 설치기 GET 점검·sudo 환경 보존, report-hub 읽기 수집,
셸의 설치 자격증명 존재 점검이다. 격리된 옛 회의 플러그인만 `automation`을
가져올 수 없고 override도 없을 때 옛 환경 토큰으로 ACK를 보낸다. override가
조금이라도 남아 있으면 그 폴백으로 보내지 않는다.
RAG Discord 수집도 읽기 전용이고,
워처의 자식 환경 전달은 최종 발신자가 다시 공용 해석기를 거친다.
수리 보고 소비자의 독립 런타임에도 해석기·노드 설정 모듈·설정 시드를 함께 배포한다.

## 읽기 전용 확인

각 노드 계정(agent·peer·ops)에서 릴리스 트리를 `PYTHONPATH`에 둔 뒤 실행한다.

```bash
python3 -m automation.notice_bot check --expected-id <유돌-봇-ID>
```

GET `/users/@me` 한 번만 실행하며 출력은
`NOTICE-BOT bot_id=<숫자-ID> match=yes|no`다. 일치 0, 불일치 1,
판정 불가 3이며 토큰·응답 본문은 출력하지 않는다. 세 계정의 일치와 배포 영수증을
확인한 후 소유자가 Developer Portal에서 예전 세 토큰을 폐기한다.
doctor·헬스체크는 활성 override에 `[PASS] 발신 봇: 유돌(덮어씀)`을 표시한다.

관련: `automation/notice_bot{,_release}.py`, `automation/deploy_all{.sh,_probe.py}`,
`automation/release{.sh,_approval.py,_spec_message.py}`,
`tests/unit/test_notice_bot*.py`.
