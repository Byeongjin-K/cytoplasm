# 수리 기록 원자적 쓰기와 실패 이유 남기기

## 무엇을

수리 카드 중복제거 기록(`~/.hermes/repair-tickets.json`)을 **임시 파일에 다 쓰고 fsync 한 뒤 이름 바꾸기**로
저장한다. 디스크가 꽉 차 쓰기가 실패해도 이전 기록이 그대로 남는다. 다이제스트 수리 워처
(`mail-triage-repair-daily`)는 `repair_cli` 가 실패하면 그 CLI 가 가려 남긴 이유를 실패 줄에 함께 싣는다.

## 왜

- `RepairRegistry._save` 가 `write_text` 로 기록을 바로 덮어써, 2026-11-19 디스크가 꽉 찼을 때 파일이 0바이트로
  남았다. 그 뒤로 `_load` 가 빈 파일을 거절해 모든 수리 요청이 실패했다.
- 워처는 실패 줄에 `MAIL-DIGEST-REPAIR-FAIL RuntimeError` 만 남기고 CLI 의 stderr 를 버려, 이틀 뒤 알림을 받고도
  원인을 노드에서 다시 찾아야 했다. CLI 도 `RepairStateError` 를 잡지 않아 가리지 않은 traceback 을 냈다.
- 빈 기록·깨진 기록은 **조용히 `{}` 로 다시 시작하지 않는다.** 시그니처를 잊으면 카드를 처음 멱등키로 다시
  만들고, 보드는 그 키를 가진 non-archived 카드(종결된 `done` 카드 포함)를 돌려준다([재발 재발급](수리-티켓-재발-재발급.md)).
  닫힌 카드의 재발이 옛 카드로 돌아가고 횟수가 1 로 돌아가므로, 막고 사람에게 넘긴다. 원자적 저장 뒤에는
  이 저장 경로가 빈 파일을 다시 만들지 않는다.

## 사용 시나리오

**happy** — 디스크가 차 있는 동안 수리 요청이 들어온다 → 임시 파일 쓰기가 `OSError`(공간 없음)로 실패하고
임시 파일은 지워진다. 기록은 이전 내용 그대로라, 공간이 생긴 뒤의 다음 요청은 같은 카드의 다음 occurrence 로
이어진다.

**실패** — 기록이 다른 이유로 비었거나 깨졌다 → `repair_cli manual` 이 `repair error: repair state is not valid
JSON (0 bytes)` 한 줄과 exit 1 로 멈추고 카드를 만들지 않는다. 워처의 실패 줄은
`MAIL-DIGEST-REPAIR-FAIL RuntimeError: repair_cli manual exit 1: repair error: repair state is not valid JSON (0 bytes)`
이고 위치는 전진하지 않는다. 운영자는 기록을 백업한 뒤 되살리고(예: `{}`), 다음 틱이 그동안의 실패를 올린다.
CLI 가 `repair error:` 줄 없이 죽으면(traceback) 실패 줄에는 예외 이름만 실린다.

## 관련

- `automation/repair/repair_core.py` — `RepairRegistry._save`(공유 도우미 `automation/credential_rotation/files.py`
  `atomic_write`), `_load`(바이트 수를 싣는 거절)
- `automation/repair/repair_cli.py` — 최상위에서 `RepairStateError` 를 가린 한 줄로
- `skills/mail/scripts/mail_digest_repair_watch.py` — `cli_failure_reason`, 실패 줄
- 회귀 `tests/unit/test_repair_tickets.py`(쓰기 중 공간 없음·빈 기록·CLI 한 줄), `tests/unit/test_mail_digest_repair_watch.py`
- 승인 게이트: 해당 없음 — 카드 발급 경로와 승인은 그대로이고, 기록을 저장하는 방식과 실패 문구만 바뀐다.
