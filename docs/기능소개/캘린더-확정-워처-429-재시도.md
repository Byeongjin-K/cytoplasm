# 캘린더 확정 워처가 Discord 429 를 기다렸다 다시 묻는다

**무엇을**: 1분마다 도는 `calendar-confirm-watch` 가 Discord 에서 「잠깐 기다려」(HTTP 429)를 받으면, 실패로 끝내지 않고 Discord 가 말한 시간(10초 이하)만큼 기다렸다가 같은 요청을 최대 3번까지 다시 보낸다.

**왜**: 2026-10-17 오전 #notifications 에 doctor 알림 「확인 · 정기 작업(워처): 최근 실패·중지: calendar-confirm-watch」가 떴다. 노드 기록을 보니 최근 145번 실행 가운데 18번이 실패했고, 18번 모두 같은 원인이었다. 승인 카드 메시지를 읽을 때 Discord 가 `429 retry_after=5` 를 준 것이다. 메일·리마인더 같은 다른 경로는 공용 전송 코드가 429 를 기다렸다 다시 묻는데, 캘린더 확정 경로(`calendar_confirm._api`)만 그 처리가 없었다. 그래서 5초 기다리면 될 일이 틱 실패(exit 1)가 됐고, Hermes 가 `last_status=error` 로 적었고, doctor 는 매시 점검이 그 직후에 걸리면 알림을 보냈다. 고장이 아니라 잠깐의 속도 제한이었는데도 소유자가 알림을 받아 확인해야 했다.

**사용 시나리오**
- 평소: 소유자가 일정 승인 카드에 ✅ 를 누른다. 그 순간 Discord 가 429 를 주면 워처가 5초 기다렸다 카드를 다시 읽고, 같은 틱 안에서 일정을 등록한다. #notifications 에는 아무 알림도 오지 않는다.
- 계속 막힐 때: 세 번 물어도 429 이거나 Discord 가 10초보다 오래 기다리라고 하면 그 틱은 예전처럼 실패로 남는다. 다음 분에 다시 시도하고, 같은 실패가 이어지면 doctor 가 알린다. 다음 틱과 겹치지 않도록 무한정 기다리지 않는다.

**관련**
- 코드: `skills/calendar/scripts/calendar_confirm.py` (`_api`, `API_MAX_ATTEMPTS`, `API_MAX_RETRY_WAIT`)
- 시험: `tests/unit/test_calendar_confirm_rate_limit.py` (실제 urllib 로 루프백 Discord 에 요청)
- 같은 규칙의 공용 구현: `automation/interop/reaction_approval.py`, `automation/interop/discord_transport.py`
- 승인 게이트는 그대로다. 다시 묻는 것은 읽기·게시 요청뿐이고 소유자 ✅ 판정은 바뀌지 않는다.
