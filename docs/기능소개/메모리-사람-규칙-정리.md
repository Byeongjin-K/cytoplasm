# 메모리 정리 — 줄마다 이동·유지·양 계정 삭제 선택

## 무엇을

USER.md 에 쌓인 **동료의 호칭·연락처·소속**은 Obsidian 사람 노트(`person--…`)로, **메일·할 일 처리 규칙**은
MEMORY.md 로 옮긴다. **한 카드에서 줄마다 이동(기본)·유지·삭제를 고르고 마지막에 ✅ 한 번** 누른다.
삭제는 agent와 peer의 USER.md·MEMORY.md에 있는 **글이 정확히 같은 항목**을 지우며 백업을 보관한다.
옮긴 사람 정보는 매 세션 프롬프트에서 빠지므로, 에이전트 `SOUL.md` 에 「사람 이름·과거 사실은 recall로 찾아라.」
한 줄을 릴리스가 넣는다.

## 왜

USER.md 는 "사용자 본인이 누구인가" 를 담는 칸인데, 2026-10-14 조사에서 15개 항목 중 동료 정보 4건과
처리 규칙 3건이 약 490자(상한의 36%)를 차지하고 있었다. 기존 재배치는 이 항목들을 옮기지 못했다 —
"선임"·"박사"·"문체"·"할 일" 같은 낱말이 들어 있으면 분류 전에 "그대로 둔다" 로 판정했기 때문이다(그 낱말은
본인 소개·응답 스타일을 지키려던 장치다). 그리고 재배치는 항목마다 카드를 따로 올렸다.

소유자 결정(Q138): 「①②③ 다 (추천: ① 오늘, ②·③은 이어서)」 — 이 문서는 ②다. 「나를 최대한 편하게
만들어줘」 에 따라 승인은 카드 한 장으로 묶는다.

## 사용 시나리오

- **정리(정상)**: 재배치 워처는 리액션을 2분마다 처리하고, 진행 중인 재배치가 없으면 30분 간격으로 분류한다. 분류기는 낱말 때문에 막혔던
  항목도 모델에게 묻고, 답이 「다른 사람에 대한 사실」(`PERSON_REFERENCE`)이나 「USER.md 에 들어온 처리 규칙」
  (`AGENT_RULE`)일 때만 그 판정을 받는다(그 밖의 답이면 예전처럼 그대로 둔다). 해당 항목 전부가 한 카드
  「메모리 정리 — 사람 정보·처리 규칙 N건」 으로 소유자 대화 채널의 요청별 스레드에 올라온다. 카드는 항목 원문과
  가는 곳(사람 노트 경로 또는 `MEMORY.md`)을 모두 보여 준다.
- **줄별 선택**: 같은 색의 원=이동, 네모=유지, 하트=삭제이며 각 줄에 뜻을 적는다.
  봇이 모든 리액션을 미리 달므로 이모지를 새로 추가할 권한이 없어도 기존 리액션을 누를 수 있다.
  선택하지 않은 줄은 이동, 한 줄에서 둘 이상 누르면 안전하게 유지한다.
- **예시**: 첫 줄의 사람 정보는 선택 없이 두고, 두 번째 처리 규칙은 네모(유지),
  세 번째 오래된 정보는 하트(삭제)를 누른 뒤 카드의 ✅를 누른다.
  첫 줄은 사람 노트로, 두 번째는 원래 자리에, 세 번째는 양 계정의 두 메모리 파일에서 사라진다.
- **이동**: 사람 정보는 노트를 쓰고 RAG 인제스트를 확인한 뒤, 규칙은 MEMORY.md 에 같은 글이 들어간 것을 확인한 뒤
  원래 자리에서 지운다(지우기 전 백업). MEMORY.md 가 상한(3,300자)을 넘으면 넣지 않고 멈춘다.
- **삭제**: 별도 노트를 만들지 않는다. 두 계정이 각자의 Hermes 잠금·스냅샷 대조·백업을 거쳐 같은 글만 지운다.
  다른 글이나 비슷한 이름은 대상이 아니다. 양쪽 완료 전에는 전체 완료라고 하지 않는다.
- **선택 확정**: peer 워처가 소유자 ✅를 처음 성공적으로 감지할 때 전체 선택을 한 번 읽어 저장한다.
  클릭한 순간의 시각을 재구성하는 방식은 아니다. 저장된 뒤 리액션을 바꿔도 선택은 바뀌지 않는다.
- **⛔**: 카드의 모든 항목이 그대로 남고, 같은 항목은 다시 제안하지 않는다.
- **승인 철회 뒤 개선된 카드로 다시 받기**: 운영자가 워처 잠금 아래 `abandoned`와
  `last_block_reason=owner-withdrew-approval`로 철회한 항목만 다시 제안한다.
  일반 취소와 줄별 유지 선택은 다시 묻지 않는다. 재게시할 때는 배치의 모든 항목이
  저장한 `approval_thread_id`를 보존해 같은 요청의 스레드를 재사용한다.
- **카드가 너무 길 때**: 한 카드(1,900자·최대 5줄)에 들어가는 항목만 이번에 올리고 나머지는 다음 주기에 올린다.
  5줄 × 3개 선택 + ✅·⛔ = 17개라 다른 리액션을 위한 여유 3개를 남긴다.
  사전 리액션 배치가 실패하면 실행하지 않고 재시도한다. 혼자서도 카드에 안 들어가는 긴 항목은 뒤 항목을 막지 않는다.
- **확인 실패**: 카드가 없거나 바뀌었거나 peer가 읽을 수 없으면 삭제하지 않는다.
  선택 수집 도중 끊기면 추측하거나 새 리액션으로 대체하지 않고 보류한다.
- **기존 카드**: 이미 게시된 v1 카드는 예전 번호 리액션으로 유지할 줄을 고르는 계약 그대로 처리한다.
- **짧은 항목**: 호칭 한 줄처럼 짧은 USER.md 항목도 모델에게 묻는다(예전에는 60자 미만이면 묻지 않았다).
- **모델 호출 수**: 판정은 항목 글(digest)·프롬프트 판본별로 한 번만 하고 캐시한다(`~/.hermes/memory-curator/classify-cache.json`). 글이 바뀌면 다시 묻고, 모델 실패는 캐시하지 않는다.
- **본인 소개**: 사용자 본인의 이름·소속·직함은 사람 노트로 옮기지 않는다(모델 판정이 본인이면 그대로 둔다).
  잘못 실린 항목이 보이면 ⛔ 하면 된다.
- **SOUL 줄**: 릴리스가 agent `~/.hermes/SOUL.md` 에 그 한 줄이 있는지 보고, 없으면 백업 뒤 끝에 덧붙인다.
  파일이 없으면 만들지 않는다(Hermes 기본 정체성을 덮지 않게). 다음 세션부터 보인다.

## 왜 peer가 직접 확인하는가

agent는 peer의 홈에 쓸 권한이 없다. agent가 쓴 「승인됨」 파일을 믿거나 sudo를 주는 대신,
**peer의 no-agent 워처가 자기 봇으로 원 승인 카드·배치 해시·소유자 리액션을 확인**한다.
선택을 두 워처가 따로 읽으면 중간에 바뀐 리액션 때문에 두 계정이 다른 결정을 실행할 수 있어,
새 판본의 선택 동결은 peer 한 곳만 맡고 agent도 그 영수증을 따른다.

릴리스가 root 없이 준비한 `/srv/autophagy-repair-report-queue/memory-choices/{agent,peer}`는
소유 계정만 쓸 수 있고, 설정된 서비스 그룹만 읽는다(디렉터리 0750·파일 0640).
부모 `memory-choices`는 ops 소유 setgid+sticky(3770)라 각 계정은 자기 요청함만 만들 수 있고
다른 계정의 요청함을 옮기거나 지우지 못한다. 서비스 그룹은 원문을 읽을 수 있는 신뢰 대상이다.
요청 파일은 권한이 아니라 검증할 카드·항목 목록이다.
peer의 사유 원장과 메일박스는 agent가 바꿀 수 없고, 잘못된 소유권·심링크·쓰기 권한은 거부한다.
메모리 홈 권한·sudoers·자격증명은 공유하지 않는다.
새 판본은 이동·유지를 포함해 peer의 선택 동결이 먼저 필요하므로 peer가 중단되면 실행이 지연된다.
두 워처가 서로 다른 선택을 실행하지 않게 하는 의도된 의존이며 v1에는 추가하지 않는다.

삭제 직전에 파일별 실행 의도를 기록한다. 삭제와 완료 영수증 사이에 프로세스가 끊기면
`delete-interrupted`로 멈추며 같은 글을 자동으로 다시 지우지 않는다. 운영자는 백업과
`memory-curator/choice-deletes`(agent) 또는 `memory-relocate-peer/deletes`(peer)의 원장을
확인해 복구한다. 소유자가 취소하면 아직 시작하지 않은 작업은 양 계정 모두 멈추지만 이미 끝난 삭제는 되돌리지 않는다.

## 릴리스가 스스로 준비하는 것 (소유자 조치 0)

소유자 지시(2026-10-14): "내가 승인한 후에 자꾸 노드에서 작업해야하는거 없으면 좋겠어".
그래서 릴리스 ✅ 뒤 배포기(`automation/memory_relocate/deploy.sh`)가 아래를 모두 한다 — root도 새 sudo 권한도 쓰지 않는다.

- peer `memory-relocate-peer-watch` no-agent cron을 설치한다.
- ops·agent·peer 순서로 `python3 -m automation.memory_relocate.choice_accounts --provision`을 그 계정으로 돌린다.
  ops는 기존 ops 인계 디렉터리(`/srv/autophagy-repair-report-queue`) 안에 공유 디렉터리를 한 번 만들고,
  각 계정은 자기 요청함만 만든다. 이미 있으면 모양만 다시 확인하고 고치거나 넓히지 않는다(어긋나면 거부).
- agent 설정의 `agent_chat_channel_id`를 읽어 peer 소유 0600 파일
  `~/.hermes/memory-relocate-peer/approval-config.json`에 그 키 하나만 쓴다
  (`automation/memory_relocate/peer_approval_config.py`). 채널 키를 일반 peer interop 설정에 넣지 않는 이유는
  게이트웨이의 무멘션 자동응답을 켜지 않기 위해서다. 값이 없거나 형식이 틀리면 배포가 멈춘다.
- peer 봇이 소유자 대화 채널의 요청별 스레드를 읽고 리액션을 조회할 수 있어야 한다(설치 때 이미 초대돼 있다).
  접근 권한이 없으면 새 카드의 실행은 멈추고 워처가 실패를 보고한다.
- 백업은 각 계정 `~/.hermes/memories/*.deleted-*`에 남는다. 복원은 운영자가 대상을 확인해 수행한다.

- 새 선택·양 계정 검증: `tests/unit/test_memory_relocate_choice*.py`,

- 승인: 기존 재배치 생산자·lifecycle·요청 스레드를 재사용한다. peer 워처는 같은 카드의 검증·실행자이며
  별도 승인 카드를 만들지 않는다. v2 `batch_hash`는 순서·항목별 해시·세 선택·기본값·충돌 처리·삭제 범위를 묶는다.
  선택 결과는 해시 밖의 동결 영수증이고, MOVE만 기존 저장·RAG 확인 경로를 지난다.
